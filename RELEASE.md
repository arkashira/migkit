# Releasing migkit

Cutting a release is one command. Everything else runs in CI.

```bash
# 1. bump the version in pyproject.toml (the release fails if it does not match the tag)
# 2. commit that
git commit -am "chore: version 0.2.0"
# 3. tag and push
git tag -a v0.2.0 -m "v0.2.0" && git push origin master v0.2.0
```

The `release` workflow then:

1. runs the guard (nothing organisation-specific, no committed credentials)
2. runs the full test suite, including the docker-backed ones
3. checks the tag matches the version in `pyproject.toml`
4. builds the sdist and wheel, validates them, and installs the wheel in a
   clean environment to prove it runs
5. generates the release notes from the commits since the previous tag
6. publishes a GitHub Release with the distribution files and their checksums

A tag containing a hyphen (`v0.2.0-rc1`) publishes as a pre-release.

## Release notes

Generated by `tools/gen_changelog.py` from commit subjects, which follow
`area: what changed`. Conventional types (`feat`, `fix`, `docs`, ...) map to the
usual headings; any other prefix becomes a heading named after that area. A
subject with no prefix still appears, under "Other" - a release note that
silently drops a change is worse than an untidy one.

Preview before tagging, or fold the notes into `CHANGELOG.md`:

```bash
python tools/gen_changelog.py v0.2.0
python tools/gen_changelog.py v0.2.0 --update
```

## Publishing to PyPI

Not automated on purpose: it publishes under a personal PyPI identity and needs
that token. Download the artifacts from the release, or rebuild locally.

```bash
rm -rf dist && python -m build
twine check dist/*
twine upload -u __token__ -p pypi-XXXXXXXX dist/*
```

Test against TestPyPI first with `-r testpypi`.

To automate it later, add the token as the `PYPI_API_TOKEN` repository secret
and a `twine upload` step to the `publish` job.
