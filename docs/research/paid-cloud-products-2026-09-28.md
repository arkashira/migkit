## 2. Products the mechanism reports did not cover

### 2.1 Informatica Cloud Data Ingestion and Replication (CDIR; formerly Cloud Mass Ingestion)

**What it is.** IDMC service with three load types - initial, incremental (CDC), initial-and-incremental - over Oracle, SQL Server, Db2 (LUW, i, z), PostgreSQL, MySQL, SAP HANA and others into warehouses, lakes and databases; priced from a prepaid pool of IPUs drawn down per "scaler" (ingestion by data volume), quote-only.

**Mechanisms migkit lacks or does shallower.**
- **CDC Staging groups**: one *CDC Staging Task* reads the source log once and writes the changes to S3/ADLS/GCS; several ingestion tasks in the group consume from there. Retention 14 days default, up to 365. This is the "read once, many consumers" spool (the GoldenGate report's row names Informatica's Logger for the same idea) with *object storage* as the spool and a stated retention - a re-sync of one target replays from storage, not from the source's log. migkit: lacks (R3 one-to-many, R19.7; the GoldenGate report proposes a spool triggered by measured `stream_room` shrinkage). New here: object storage as the spool target, and retention measured in days, which removes the source-retention limit from long rehearsals.
- **Apply modes Standard / Audit / Soft Deletes**: Audit writes every DML as a row with `opType` and metadata columns; Soft Deletes writes `INFA_OPERATION_TYPE='D'` instead of deleting. Soft Deletes requires immutable primary keys, and in combined loads the job *manufactures* a delete for a row captured during the unload, which appears on the target as a soft delete that never happened at the source. migkit: none (the CDC/ELT report lists history/soft-delete/SCD2 as "none"). migkit's rule stays: a migration target mirrors the source; an audit trail belongs on a Kafka/Parquet/DuckDB leg.
- **Schema drift options per DDL kind** (Add, Modify, Drop, Rename column) x (Ignore, Replicate, Stop Job, Stop Table), and *Resume With Options* to override after a stop. Detection happens only when a DML hits the altered table; several DDLs without DML in between are seen at once; key changes are never replicated (target resync). migkit: `_shape_gate` stops the tail on any shape change (`hetero.py:2808`), DDL is generated with a backfill warning (`migkit/ddl.py:102`). **Behind** on "Stop Table" granularity: migkit stops the whole tail where Informatica isolates the one table and keeps the others flowing.
- **Restart and recovery**: records the change-stream position as changes are applied; restarts without loss. Tables cannot be moved between jobs without resync. migkit: equal (token file + upsert replay), and ahead on moving work (ranges re-plan under a fingerprint).
- **Monitoring**: alerts tab lists every detected schema change even when set to Ignore; IPU metering alerts at 25/50/75/95/100 %. migkit: `watch` and notify; no "schema change seen" alert when the gate is not tripped.
- **Verification**: none in CDIR itself (Data Validation is a separate product). migkit **ahead**.

**Verdicts.** F1 ahead; F2 equal-unknown (no public rates); F3 equal; F4 equal; F5 n/a (no conversion); F6 behind (Db2 z/i, SAP, mainframe sources); F7 ahead (no cutover tooling documented); F8 behind (per-table stop, schema-change alerts, staging groups); F9 per A2 not scored there; F10 ahead (IPU contracts, quote-only).

### 2.2 Precisely Connect CDC (formerly Syncsort MIMIX Share) and Connect CDC SQData

**What it is.** Two lines: Connect CDC (MIMIX Share) - capture, transform, distribute across IBM i, AIX, Linux, Windows; Db2 for i/LUW, Informix, Oracle/RAC, SQL Server, Sybase, Teradata/MySQL as targets; topologies one-way, two-way, cascade, bidirectional, distribute, consolidate. Connect CDC SQData - mainframe sources (IMS, VSAM, Db2 z) through *capture agents*, a *publisher*, and *apply engines* scripted in its own language, with *replicator engine* "distributors" (e.g. IMS to PostgreSQL). Documentation behind a login/JavaScript; no public rates.

**Mechanisms migkit lacks.** Hierarchical and mainframe sources (IMS segments, VSAM records) flattened to relational targets by a scripted apply engine; cascade and consolidate topologies (many sources into one) as named configurations; Kafka schema-registry integration with Kerberos. migkit: IMS/VSAM out of scope; consolidate = R3 many-to-one with a DDL owner (not built, `mechanisms-dts...` row "Pessimistic shard-DDL lock").

**Verdicts.** F1 ahead (no public verification feature); F3 unknown; F6 behind (mainframe, IBM i); F7 behind on topologies (cascade/consolidate), equal on two-way; F10 ahead.

### 2.3 Confluent: Cluster Linking and fully managed Debezium (CDC Source V2)

**Cluster Linking.** Mirror topics are *byte-for-byte, offset-preserving* copies: same message, same partition, same offset; compressed batches are not recompressed. Consumer offset sync (at most once a second, filterable by group) writes source group offsets to the destination; on `promote`/`failover` the offsets are **clamped** to the mirrored log end, so a group never resumes past what was actually mirrored. `reverse-and-start`/`reverse-and-pause` swap direction; `truncate-and-restore` makes the old source mirror the new one after a failover. Pitfalls documented: a group already active on the destination leaves the topic in `PENDING_MIRROR`; producing during `PENDING_STOPPED` fails; check "consumer lag > mirroring lag" before moving consumers.

migkit today: Kafka engine copies messages (new offsets on the target) and *translates* each group's committed offset by finding the same message on the target by timestamp then key and value (`migkit/engines/kafka.py:904`), refusing when the message is not found (`:1025-1037`); consumer-group parity is a deep check (`:934`). So:
- **behind** on fidelity when both ends are Confluent (no translation needed, compression untouched, clamping built into promote);
- **ahead** on reach (any Kafka to any Kafka: MSK, Redpanda, self-managed; Cluster Linking needs a Confluent destination) and on proof (migkit's parity check says which groups would re-read or skip; Cluster Linking asserts);
- **behind** on the clamping rule: migkit should state for each group, at cutover, "committed offset beyond what the target holds -> put at the target's end, N messages would be skipped" - the same rule, said in the verdict.

**Managed Debezium (CDC Source V2).** PG 12-18, `pgoutput`/`decoderbufs` only; exactly-once only in streaming mode, only for connectors created with EOS, never during snapshots (Kafka Connect KIP-618 underneath; Debezium itself says edge cases are unproven); incremental snapshots through a signal table added to the publication; one connector per slot; V1 end of life 31 March 2026 with breaking defaults. migkit wraps Debezium already (`migkit/movers.py:3173` config generation, `:3349` re-snapshot signals). **ahead** on the snapshot phase (migkit's own copy is resumable and verified; Confluent's snapshot is at-least-once and restarts), **behind** on managed operation (no hosted runtime - by design).

**Verdicts (Cluster Linking).** F1 ahead (no compare); F2 behind for Kafka->Kafka (byte copy, no recompress); F4 behind (offset identity); F6 behind-narrow (Kafka only, both ends Confluent/CP); F7 behind (promote/failover/reverse primitives with clamping); F10 ahead.

### 2.4 Airbyte Cloud (additions to the CDC/ELT report s.1.6)

New since that report: **Direct-Load** replaced Typing-and-Deduping on all 11 certified destinations (July 2026): no raw JSON table, typed and deduped final tables while the sync runs, per-record `_airbyte_meta` errors; a type change that cannot cast historical values fails the schema change. **Refreshes** in two kinds - *Refresh and Retain* (merge) and *Refresh and Remove* (delete first) - resumable where source and destination checkpoint; they block scheduled syncs. **Resumable Full Refresh** checkpoints on the last page and is at-least-once, with *Overwrite + Dedup* offered to remove the duplicates it creates. Pricing: Standard is volume-based ($10/GB for database sources per the pricing page), Pro/Enterprise Flex capacity-based "Data Workers" (~3 concurrent syncs each); on volume plans every re-sync is paid again.

migkit: refresh-and-retain = `sync --kind rows` on a differing table with undo; refresh-and-remove = truncate step (`migkit/movers.py:619`) then ranged copy; `_airbyte_meta`-style per-row error capture deliberately absent (copy stops and names the key). **ahead** on exactness (no at-least-once duplicate phase to dedupe later); **behind** on per-record error isolation for lake/warehouse targets (the aws report already proposes "optional, off by default, only for file/lake targets"); **ahead** on cost of re-runs (a re-verify costs digests, a re-copy costs no licence).

### 2.5 Hevo

**Mechanism.** PostgreSQL: *Logical Replication* (default; slot created and dropped by Hevo), *Table* (per-table schedule and query mode), *Custom SQL*, *XMIN* (early access); query modes Full Load, Delta-Timestamp, Unique Incrementing Append Only decide the historical read. Loads through a temporary table and upsert by primary key; deletes become `__hevo__marked_deleted = true`; exactly-once only for keyed events, at-least-once otherwise; keyless tables are deduplicated only after a key is declared, then truncate + historical reload. **Schema Mapper**: auto-creates tables, **widens** destination column types to fit data variations, marks incompatible events Failed; failed events are kept **7 days** and replayed automatically every ~5 min after the mapping is fixed. Documented hazards: a pipeline paused > 24 h may lose data (log purged); a DB upgrade invalidates the slot silently; no logical replication from read replicas; changing a query mode re-reads the object from the start.

**What migkit does not do.** XMIN-based change reading (PostgreSQL `xmin` as a cursor without a slot: a no-log rung, related to Arcion delta-snapshot); automatic *type widening* on the target when a value does not fit (migkit stops and names the column; `canon.py` maps once); a failed-event queue with automatic replay after a fix (migkit stops the lane, R2.3). **ahead**: slot health is measured (`postgres.py:1311` `stream_room`) rather than "pause > 24 h may lose data"; keyless tables are handled by count-settled spans (`ranges.py:260`) not "declare a key then reload"; verification exists.

**Verdicts.** F1 ahead; F3 equal-unknown; F4 ahead (exact on keyed and keyless); F5 behind-narrow (auto widening); F6 behind (150+ SaaS sources; out of scope); F8 equal (failed-event replay vs migkit's stop-and-name); F10 ahead (event-based pricing).

### 2.6 Matillion (Data Productivity Cloud: CDC / Streaming pipelines)

**Mechanism.** A self-hosted *agent* (container in the customer's VPC, x86 only, 4 vCPU/8 GB recommended) running **Debezium** connectors; changes written as files to the customer's cloud storage, then loaded by Matillion jobs. One streaming pipeline per agent. Documented limits: an interrupted snapshot starts again from zero; re-creating a pipeline without clearing its storage reuses `offset.dat` and **silently skips the snapshot**; unmodified TOAST values arrive as `__value_not_modified__` (older agents `__debezium_unavailable_value`) and can overwrite real values unless the table is `REPLICA IDENTITY FULL`; SQL Server computed columns captured as NULL; snapshots billed by rows.

**migkit.** Already beats every item: resumable snapshot by range (`checkpoint.py:51`), slot-before-snapshot, partial-update merge for unchanged TOAST (`base.py:3917`; the CDC/ELT report flags the `unchanged-toast-datum` token in `pgslot.py` as "to measure"), leftovers counted (`migkit/leftovers.py:67`). The one thing to take is a *negative*: the stale-offset-skips-snapshot failure is exactly what `tailctl.same_source` (`migkit/tailctl.py:174`) guards; worth a test that a token from a previous hop incarnation is refused, not reused.

**Verdicts.** F1 ahead; F2 ahead; F3 equal (Debezium); F4 ahead; F6 behind (warehouse targets, SaaS); F8 behind (hosted UI); F10 ahead (credits).

### 2.7 Rivery (Boomi Data Integration since Dec 2024)

**Mechanism.** Two river modes: *Standard Extraction* (SQL queries, scheduled) and *Change Data Capture* (log-based: MySQL binlog with `binlog_row_image=FULL`, 7-10 day retention recommended). The CDC reader streams to a *FileZone* in time frames of up to 15 minutes and the target is loaded on the data flow's schedule - so latency is minutes by design. **Automatic schema drift**: target schema altered to match the source without stopping. **CDC Point in Time position** exposed through the API (`binlog_file`, `binlog_position`, `gtid`) to restart from an exact position.

**migkit.** Exact position restart: equal (`tailctl.py`, token). Minute-scale latency: migkit ahead (sub-second behind on the measured tails, B1). Automatic additive schema drift: behind (migkit stops; the CDC/ELT report proposes "optional additive auto-ALTER" behind the gate).

**Verdicts.** F1 ahead; F3 ahead; F4 equal; F5 behind-narrow (auto drift); F6 behind (SaaS); F10 ahead.

### 2.8 Arcion, now Databricks Lakeflow Connect database connectors

Arcion's delta-snapshot mode is in the GoldenGate report (s.1.6). Arcion was bought by Databricks (announced Oct 2023, ~USD 100M) and is no longer sold on its own; its CDC engine powers Lakeflow Connect's managed connectors for MySQL, PostgreSQL, SQL Server (CDC or Change Tracking, or full snapshot) and Oracle (LogMiner).

**Mechanism (new here).** Two pipelines: an always-on **ingestion gateway** on classic compute that extracts snapshots, change logs and metadata "before change logs can be truncated", writing to a **staging volume** (Unity Catalog volume, purged after 30 days); a separate serverless **ingestion pipeline** applies from staging to streaming (Delta) tables on any schedule. July 2026 added an **integrated** SQL Server pipeline: one pipeline, triggered, runs until caught up and stops, bounded by a maximum runtime (60 min suggested).

**What migkit does not do.** Decouple capture from apply through a durable spool with its own retention (same gap as Informatica CDC staging, 2.1); a "run until caught up, then stop" triggered tail with a time bound. migkit's tail is continuous; `schedule.py` can start it on a slot (`migkit/schedule.py:71`), and `watch --count` ends a watch, but a tail that *exits by itself when caught up* (the fence reached and nothing newer) is not a documented behaviour - worth a rung for rehearsals that run nightly. **Delta/Databricks as a target**: migkit has Parquet and DuckDB, not Delta (F6 behind for lakehouse targets).

**Verdicts.** F1 ahead (no compare documented); F3 equal-unknown; F4 equal (staging gives recovery; migkit's token + upsert gives the same without storage); F6 behind (Oracle LogMiner live, Delta target); F8 behind (scheduled triggered tail); F10 ahead (DBU-billed, Databricks-only).

### 2.9 Datafold: cross-database data diff and the Migration Agent (DMA)

**Data diff.** The open-source `data-diff` (hashdiff) splits a table into key segments, checksums each on both sides (MD5 over the chosen columns), recurses into differing segments by `bisection_factor` until a segment is under `bisection_threshold`, then downloads and compares rows; `joindiff` (outer join) within one database. Known weakness: long key gaps cause many empty-range queries; the docs list "faster hash than MD5" and adaptive factor/threshold as not built. The OSS repo is stale; the cloud product uses "stochastic checksumming" and claims up to 10x faster cross-database diffs (2024).
migkit wraps `reladiff` (the maintained fork of hashdiff) for the generic engine (`migkit/engines/generic.py:44`) and has its own bisect for integer keys (`hetero.py:462`), sum-fold digests rather than XOR (`checkpoint.py:118`), segments fingerprinted so a changed plan refuses stale partials (`checkpoint.py:39`), and the fence that tells in-flight from wrong (`base.py:3194`). **ahead** on proof while the source is live (data-diff compares a moving target and reports noise as differences); **behind** on key types (data-diff bisects any orderable key including text/UUID; migkit's own bisect is integer-only - the DTS report's "stats edges" item closes this).

**Migration Agent (DMA, Oct 2024; 2.0 in 2025).** An LLM translates SQL, stored procedures and ETL (Informatica, SSIS, Talend) into the target dialect or into dbt models; the **Source Aligner** first freezes input datasets on both systems and proves them identical; then legacy code and new code run on the frozen inputs and outputs are diffed "row by row, value by value"; on a mismatch the agent **regenerates the code and repeats until parity**; residue is "documented and explained". Priced fixed per legacy object count; supervised by Datafold staff; days to weeks.
migkit has the proof half (`prove_converted`, `hetero.py:2315`: views by rows, functions by their answers to the same arguments; procedures "answer nothing to compare") and the proposal half (`assist.py:112`, proposals never a verdict). What it lacks: **the loop** (propose -> prove -> feed the failing diff back -> propose again, bounded), **frozen aligned inputs** for procedures that write (R11's "run in a transaction rolled back, digests of the tables it touched"), and **procedures as comparable units** (today skipped). This is the single most valuable mechanism in this file for R11: see gap table row 1.

**Verdicts.** F1 equal on diff (ahead live, behind on key types); F5 behind (DMA converts procedures with an execution-proved loop; migkit proves views/functions but does not loop and skips procedures); F6 behind for warehouses/ETL code; F10 ahead (fixed per-object fee + staff).

### 2.10 SQLines (SQL Converter + SQLines Data)

**SQL Converter** (online, desktop, CLI): converts DDL, queries, DML, views, procedures, packages, functions and triggers between Oracle, SQL Server, Sybase, Db2, Teradata, MySQL, PostgreSQL and others; works on SQL *scripts* with no database connection; examples of its rules: `CALL` inserted before a procedure invoked by name, Oracle's default sequence `MAXVALUE` commented out because it overflows `BIGINT`. **SQLines Data** (C/C++): native bulk APIs (OCI, libpq in-memory `COPY`), parallel sessions with concurrent read and write per session, **large tables split into chunks by identity column** with `-large_tables_parallel/_rows/_mb/_resources_pct`, a `sqlines_tchunks.txt` for explicit split conditions, a July 2026 `sqldata_tables_in_progress.txt` progress file, `WHERE` per table for incremental transfer, and validation (row counts, per-column aggregates). Evaluation builds may skip one row per table.
migkit: equal or ahead on data (equal-row ranges from the key, sized by measurement rather than `-large_tables_*` thresholds, `ranges.py:222`, `sizing.py:192`; digest verification); **behind on procedural code conversion** (SQLines has rule sets per dialect pair for PL/SQL, T-SQL, SPL, packages, triggers; migkit converts only views and single-expression functions, `hetero.py:2160`). SQLines has no proof of equivalence; migkit's `prove_converted` would be the check on top of its output.

**Verdicts.** F1 ahead; F2 equal; F4 ahead (no checkpointed resume documented beyond the in-progress list); F5 behind (procedures, packages, triggers); F6 behind (Teradata, Sybase ASA, Informix sources); F10 ahead (paid desktop licence).

### 2.11 DBConvert Studio / DBSync / DBConvert Streams

**DBConvert/DBSync** (desktop, per database pair licence): one-shot conversion and scheduled sync (insert, update, delete, mixed, bidirectional) between MySQL, PostgreSQL, SQL Server, Oracle, SQLite and others. **Bidirectional sync is trigger-based**: INSERT/UPDATE/DELETE triggers on every synchronised table write to a `history_store` table in *both* databases; conflicts are resolved by the history's timestamps (so a clock change requires clearing history and re-adding triggers). Neither product carries procedures, functions or triggers. **DBConvert Streams** (self-hosted, 2.x): reads binlog/WAL, normalises events, carries them through embedded NATS JetStream with durable checkpoints and per-table ordering to databases, files, S3; one-time load, CDC, or load-then-CDC with resumable chunked snapshot on MySQL; **no DDL after start**; a Compare tab of row counts and *samples*; Stream Monitor (throughput, lag, run history); 2.4 adds a read-only MCP server so an assistant can query the databases.
migkit: **ahead** on two-way (log-based origin marks, no triggers on the source, conflict policies and counters, `twoway.py:217`, `:354`; clock-independent where a log position exists), on verification (digests, not samples), on DDL (gate + generated DDL). **Equal** on MySQL<->PostgreSQL CDC shape. **Behind**: nothing mechanical; a desktop GUI with saved jobs is out of scope (the owner's rule: no new modes; `migkit ui` exists hidden, `cli.py:2886`).

**Verdicts.** F1 ahead; F3 equal; F4 equal (Streams) / ahead (DBSync); F5 behind-narrow (none of them convert code either: equal); F7 ahead (DBSync two-way needs triggers + clocks); F9 ahead (no source triggers or history tables: footprint); F10 ahead.

### 2.12 Ispirer (SQLWays Wizard, Toolkit, CodeWays)

**Mechanism.** A deterministic **rule-based** converter ("same input, same output, today or next year") for schema, PL/SQL packages, procedures, functions, triggers and views, plus the data; Oracle-specific constructs (`CONNECT BY`, dynamic SQL, collections, built-in packages) handled by rules; where automation stops, Ispirer engineers **add customer-specific rules within 3-5 business days**; an AI assistant (Gemini partnership, Sept 2024; can run on a local model) is positioned for *after* conversion (errors, refactoring), not for the conversion itself. Also application code (embedded SQL in Java/C#/COBOL via CodeWays). Claims (vendor only): "up to 95 %" automation on supported paths; the homepage says ~70-80 %, up to 90 % with AI; 3,000-5,000 lines/day per developer vs 300-400 by hand; a customer reports 1.49M lines and 99 % of objects. Named hand-work items: autonomous transactions, `DBMS_*` calls, `CONNECT BY`, runtime dynamic SQL, optimizer hints, Oracle-specific behaviour.
migkit: **behind** on procedural conversion and on application-embedded SQL (none); **ahead** on proof (Ispirer asserts a percentage; migkit executes and compares, `hetero.py:2315`) and on determinism of the AI boundary (migkit already keeps AI output as a proposal never a verdict, `assist.py:112`, the same line Ispirer draws). Ispirer's "custom rules in 3-5 days" is the lesson for R11: the rule base must be *extensible per project* without a new CLI mode - a hop option that points at a rules file (sqlglot transforms) is enough.

**Verdicts.** F1 ahead; F2 behind-unknown; F5 behind (packages, triggers, app code, custom rules); F6 behind (Informix, Progress, Sybase ASA, COBOL/embedded SQL); F10 ahead (paid per project).

### 2.13 EDB: Migration Portal, Migration Toolkit (MTK), Data Migration Service (DMS), LiveCompare

**Migration Portal (v5.x; web and inside Hybrid Manager).** Oracle DDL extracted by a script and uploaded; **repair handlers** (each with an `ERH-nnnn` code, e.g. ERH-2035 `BINARY_FLOAT` -> `REAL`, ERH-2036 `BINARY_DOUBLE` -> `DOUBLE PRECISION`) rewrite Oracle syntax *before* the check; the **compatibility percentage** = DDL statements that then run on EDB Postgres Advanced Server / total DDL statements; a warning below 70 % or when a DDL fails after several attempts; the report counts distinct handlers applied per schema; a missing dependent object shows as an incompatibility (include the dependent schema). Oracle 21c constructs recognised from HM 2026.8 (multivalue indexes, `ANY_VALUE`, `WINDOW`), blockchain tables and `SQL_MACRO` flagged; Oracle 23ai not supported by the Portal. **AI Copilot**: a chatbot over EDB docs and the support KB (Azure AI by default, any OpenAI-compatible model, local allowed), for workarounds only; EDB says test every suggestion. Claimed: 52M+ DDL constructs analysed; target is EPAS, whose Oracle compatibility (packages, `%TYPE`, `DBMS_*`) is what makes the percentage high - the conversion is partly *done by the target engine*, not by the converter.
**MTK** (Java CLI): offline (scripts) or "online" (direct) snapshot copy; thread pool `-loaderCount`, per-table chunks `-tableLoaderLimit`, `-parallelLoadRowLimit` (default 100,000 rows before a table is split), `-fetchSize` (Oracle JDBC default 10 makes loads crawl), `-copyViaDBLinkOra` (EPAS pulls through OCI with COPY, faster than JDBC, superuser needed). No change capture.
**DMS** (Hybrid Manager only): Debezium-based agent (`cdcagent`) reading Oracle (LogMiner) or PostgreSQL into Kafka/object storage, snapshot or snapshot + streaming until cutover. Destination tables are created **without constraints** so the snapshot is not slowed; PK/UK are added after the snapshot so streaming is exactly-once by key; keyless tables are at-least-once and "require deduplication during verification"; after cutover a **Schema Finalization** stage validates deferred foreign keys, syncs sequences, and finishes light tasks. **LiveCompare** compares PostgreSQL/EPAS/PGD/Oracle and emits a DML fix script.

**What migkit lacks or does shallower.** Oracle as a live source and PL/SQL conversion (R11/R12); a *compatibility percentage* per schema computed after the rewrite rules by actually running the DDL on the target (migkit's `handwork.py` counts and names but deliberately does not estimate; a count of "statements that ran on the target after conversion / all statements" is a *measured* figure, not an estimate, so it fits the rule in `handwork.py:11-17`); named rewrite rules with stable codes in the report (migkit's decisions carry reasons, `planner.py:27`, but conversion rules have no IDs). **Ahead**: keyless tables exact (count-settled spans, `ranges.py:260`) where EDB DMS says "at-least-once, dedupe in verification"; verify built in (EDB needs LiveCompare); constraints-after-load is equal (`movers.py:819` index window, measured per engine).

**Verdicts.** F1 equal (LiveCompare + fix script ~ migkit check + repair + revert; migkit ahead live via fence); F2 equal (MTK chunked threads; dblink_ora is EPAS-only); F3 equal-unknown (Debezium); F4 ahead on keyless; F5 behind (Oracle DDL/PLSQL with 1000s of handlers, though onto an Oracle-compatible target); F6 behind (Oracle live source), ahead elsewhere (EDB is Oracle/PG only); F7 equal (finalization stage ~ migkit sequences + FK after cutover); F10 ahead (EPAS subscription).

### 2.14 MongoDB Relational Migrator and Atlas Live Migration

**Relational Migrator** (free desktop/server app; sources Oracle, SQL Server, MySQL, PostgreSQL, Sybase ASE, Db2; target MongoDB/Atlas). **Mapping rules** restructure the model rather than copy 1:1: every FK becomes a reference by default; tables can be *embedded* as documents or arrays, split, merged, with JavaScript calculated fields; a recommended schema can seed the design. **Snapshot** or **continuous** jobs (Debezium capture; Kafka/Confluent mode recommended for large or long runs; CDC jobs failed within 24 h can be recovered, automatically in Kafka mode). **Query Converter** (generative AI, needs an Atlas login): converts SQL queries, views, stored procedures and triggers into MongoDB query/aggregation code in JavaScript, C# or Java, *aware of the mapping rules* (a join disappears when the tables were embedded), triggers become Atlas Triggers; **Test Query** runs converted queries against MongoDB; stated limits: long/complex procedures, packages may fail or be wrong. 2026: truncation detected and reported as error/warning/suppressed (Apr); **data verification compares all fields**, skips unsupported collections instead of blocking, table filters (Aug); Oracle permission issues listed up front.
**Atlas Live Migration** (pull, mongosync underneath; recommended <= 5 TB or <= 3 shards): Atlas provisions migration hosts and sequences the commands; verification only in pull mode and **not resumable**; embedded verifier needs 10 GB + 500 MB per million documents and a larger destination oplog, can false-fail on field order across nodes, fails with TTL collections when `buildIndexes=never`; unique indexes built non-unique during sync and `prepareUnique` at commit; no Search indexes; no `$`-prefixed fields; no minor-version upgrades mid-migration.

**migkit.** Wraps mongosync (`migkit/movers.py:2472`, `_mongosync_unfit` `:2430`) and has its own tail (`migkit/engines/mongodb.py:1878`), a resumable ranged copy and a verify that restarts from its checkpoint (`checkpoint.py:51`) and a delta verify from the change-stream token (`mongodb.py:1555`) - **ahead** of the embedded verifier on resumability and memory (no 10 GB floor). **Behind**: relational -> document *restructuring* (embed/array/merge by rules; migkit carries a SQL row as a flat document through the neutral layer - no "embed child table as array" mapping found by grep), and SQL-code -> MongoDB-code conversion aware of that mapping. Both are ETL-adjacent; the backlog says ETL is out of scope (`docs/backlog.md:2532` "ETL is out of scope") - worth keeping out, but the *verification* of an embedded mapping (child rows = array elements, by digest) would be in scope if the mapping ever arrives.

**Verdicts.** F1 ahead (resumable, no memory floor, field-order-agnostic canonical form `migkit/canon.py`); F3 equal (mongosync underneath or own tail); F4 ahead; F5 behind (restructuring + AI code conversion with test query); F6 equal for Mongo<->Mongo, behind for RDBMS->Mongo remodel; F7 equal (commit/`canWrite` vs fence + freeze); F10 ahead on Atlas LM (free but Atlas-only destination) - equal.

### 2.15 Redis Software / Redis Cloud: Active-Active (CRDB), Replica Of, RDI

**Active-Active.** CRDT-based multi-master across >= 2 participating clusters: counters converge by summing (59-bit range, smaller than Redis' 64-bit), sets are add-wins observed-remove, hashes merge per field, strings and bitfields last-write-wins by **OS wall clock** ("the only case" where clock time decides), strong eventual consistency; a per-node **syncer** keeps a replication backlog, partial sync normally, full sync when a replica is lost. **Migration into A-A** uses *Replica Of*: the A-A database is **flushed**, one instance replicates from the source, the syncer fans out; applications on the A-A side must be read-only until migration is turned off; major drift or a sync restart flushes and resyncs.
**RDI (Redis Data Integration, 2.0 Sept 2026; GA on Redis Cloud June 2026).** Debezium collector -> Redis streams in an RDI database -> stream processor with declarative jobs (source/transform/output) -> Redis; snapshot then CDC; ~10k records/s per processing unit (1 core, ~1 KB records); 2.0 sets Debezium `record.processing.threads=4` for faster snapshots; Spanner via change streams (Flink collector), Snowflake via Streams (preview). Write-behind (Redis -> RDBMS) is a separate Redis Gears component, at-least-once.

**migkit.** Redis engine: keys moved by scan with TTL kept (`migkit/engines/redis.py:214`), native `REPLICAOF` hop (`:872`), keyspace-notification listener for delta verify (`:1078`, `:1171`), batch compare (`:437`), drill-down and repair (`:612`). **Behind**: multi-master Redis (CRDT semantics are a server feature; migkit's two-way is for SQL engines, `twoway.py:101` refuses what cannot mark origin); relational -> Redis with transformation jobs (ETL-adjacent). **Ahead**: migkit's Redis move does not flush the target first and verifies after; Replica Of into A-A "flushes on drift" and has no compare.
One mechanism worth taking: **counters converge by summing both sides' deltas** - migkit already does this for SQL counters in two-way (`twoway.py:94` `deltas`), which is exactly the CRDT counter; it should be named as such in `docs/cutover.md` and applied to Redis `INCRBY` keys if Redis two-way is ever built.

**Verdicts.** F1 ahead; F3 behind-unknown (syncer is in-server); F6 behind (A-A); F7 behind (multi-master with defined merge per type); F10 ahead.

### 3.2 What the field converges on, and where migkit already leads

1. **Rules first, AI second, never AI alone.** Every vendor (AWS, Google, Microsoft, EDB, Ispirer, SnowConvert, Lakebridge) runs a deterministic engine and uses a model only for what the rules left. Ispirer states the reason: same input, same output next year. migkit's order is the same (`converted_code` then `assist.propose`), and its line "a proposal, never a verdict" is stricter than anyone's.
2. **Validation is mostly syntax or compile.** AWS: syntax; Huawei, EDB, MOLT: compile; Google: a model's judgement. Only **SSMA Tester** (rules era), **SnowConvert AI** (2-sided for SQL Server), and **Datafold DMA** run the same inputs on both sides and compare outputs. migkit is in that small group for views and functions already, and alone in doing it without writing to the source.
3. **The loop is the new frontier.** Datafold regenerates until the diff is empty; SnowConvert "AI-driven resolution of errors identified" after its tests; Google's Gemini propagates a human fix to similar objects. migkit has both halves and no loop.
4. **Residue has three classes, not two.** SnowConvert's split is the clearest: EWI (did not convert), **FDM (converted, compiles, may behave differently)**, and clean. AWS's INFO "AI-generated, review" and Huawei's Risk Report are the same middle class. migkit's `prove_converted` is precisely the machine that moves an object *out* of the middle class - "compiles and was proved equal on these inputs" - which no report above can say.
5. **Effort is reported, and the good ones separate learning from repetition.** AWS: learning-curve effort per action-item kind + effort per occurrence; ora2pg: cost units; Voyager: LOW/MEDIUM/HIGH; EDB: % of DDL that ran. migkit refuses to invent person-days (`handwork.py:11-17`); two measured figures fit its rule: **% of converted statements that ran on the target** (EDB's), and **per-kind time recorded when the team fixed the first one** (AWS's shape, filled with the team's own number).
6. **Project rules.** Google mapping files, Ispirer custom rules, AWS conversion settings, UGO parameters: every mature converter lets a project add or override rules. migkit's equivalent without a new mode: a hop option naming a Python file of sqlglot transforms, applied after the built-in ones and recorded in the evidence.
7. **Emulation schemas.** AWS and SSMA install extension packs (schemas of functions) in the target. migkit's footprint rule prefers inline rewrites; where emulation is unavoidable (e.g. Oracle `DECODE` on a target without it is inline; `DBMS_OUTPUT` is not), the schema should be migkit-named, counted by `leftovers.py`, and removable by `rollback`.
8. **Mapping-aware code** (MongoDB RM): converted code must use the target's names after the move's renames and remodels. `converted_code` already renames tables through `_rename` (`hetero.py:2160-2200`) - equal.
9. **Workload SQL, not only stored code.** Voyager parses the source's statements from `pg_stat_statements`; SCT converts embedded application SQL. migkit already reads the source's busiest statements and replays them on both sides for performance (`migkit/workload.py:40`, called from `postgres.py:4026`, `mysql.py:3005`) - **same engine only**. Translating those statements with sqlglot and running them on a *heterogeneous* target (answers compared by digest, like views) turns an existing check into the application-compatibility proof no vendor has.

### 3.3 What R11 should be, from the above (no new modes or flags; chosen from facts)

- **Rung order per object** (the decision layer's ladder, P0 "Decided 2026-09-27", `docs/backlog.md:105`): (a) identity - same dialect, nothing to do; (b) sqlglot rules (+ project rules file); (c) ora2pg for Oracle/MySQL/SQL Server sources when installed (`movers.tool_flag`-style probe, `movers.py:1894`); (d) AI proposal when a provider is configured; (e) hand work. Each rung's output is **proved** before it is accepted; a failed proof falls a rung, said in the report.
- **Proof for procedures** (the gap every tool but SSMA/SnowConvert/Datafold leaves open): run the routine on both sides inside a transaction that is rolled back, compare OUT parameters, result sets, raised errors, and the digests of every table the routine touched (read from the catalogue's dependency list), with inputs from the parameters' types and values sampled from the real rows. **Source-side safety chosen from facts**: when the catalogue proves the routine read-only (PG `STABLE`/`IMMUTABLE`, MySQL `READS SQL DATA`/`NO SQL`, SQL Server schema-bound with no DML), run it on the source; otherwise never on the source (sequences advance even in a rolled-back transaction; autonomous transactions and `DBMS_*` side effects escape it; SSMA Tester's "modifies source schema and data" is the failure) - run it on a **scratch same-engine copy** of the tables it touches (made from migkit's own copy of those tables) or skip with the reason.
- **The loop**: on a failed proof with an AI provider configured, send the definition, the target's error or the first differing input/output pair (never rows beyond that pair; `assist.shares` already bounds what leaves, `assist.py:105`), take the new proposal, prove again; bounded to N tries; every attempt in the evidence.
- **Report**: three classes (not converted / converted, not proved / converted and proved on K inputs), per-kind counts with stable rule IDs, % of converted statements that ran on the target, and per-kind effort only where the team's own fix time was recorded.
