# Cutover with no data problem and the shortest write outage

> **Status: COMPLETE (2026-09-28).** Sections 1-13 are the research
> (what migkit has, freeze, switch, drain proof, measured outages,
> counters, jobs, caches, open transactions, DDL, reverse leg and
> rollback, rehearsal, verification); section 14 is the design, the
> docker test plan and the effort. Public sources only.
>
> Four things found in migkit's code while doing it, each a way a
> "clean" cutover can still lose or collide data today:
> 1. the PostgreSQL fence position is `pg_current_wal_lsn()`; with
>    `synchronous_commit = off` an acknowledged commit can sit past it -
>    it should be `pg_current_wal_insert_lsn()` (section 4);
> 2. the PostgreSQL fence reads only *active* slots, so another
>    consumer's caught-up slot can pass it while the hop's own is
>    reconnecting (section 4);
> 3. `rollback` (and step 13 of `docs/cutover.md`) restores the target's
>    counters but nothing raises the old source's, so the first insert
>    after going back through the reverse leg collides (section 6);
> 4. there is no source-side freeze or proof of one: step 6 of
>    `docs/cutover.md` is outside migkit, and the fence position is taken
>    whenever `check` runs, not after a freeze (sections 2, 4).
> All four need a docker measurement before a fix.

The owner's bar: "cutover without any data problem, for real", with the
write outage as short as the source allows. This file is public research
only; nothing in it comes from any company's systems.

## 1. What migkit has today (read from the code, 2026-09-28)

The shape that follows from this: the pieces exist and are measured one
at a time. What is missing is (a) a source-side write freeze migkit chooses
and proves, (b) a drain proof taken *after* the freeze, (c) the steps run
back to back with a clock on them, (d) the reverse leg proven before the
flip, and (e) the flip itself, or at least a hook for it.


## 2. Write freeze: how each method works and how it fails

The freeze is the start of the write outage. It has to (a) stop every new
write, (b) end or finish every write already in flight, and (c) be
provable, i.e. something migkit can read back to show that nothing got
through. A method that does (a) without (b) is the most common source of a
"clean" cutover that lost a row.

### 2.1 In the database

| Method | Reaches sessions already connected? | Transactions already open | Who can still write | Undo | Documented failure modes |
|---|---|---|---|---|---|
| PG `ALTER DATABASE/ROLE ... SET default_transaction_read_only = on` | **No**: applied only at session start ([config-setting](https://www.postgresql.org/docs/current/config-setting.html)). migkit measured this (`freeze.py`) | keep writing | anyone who runs `SET transaction_read_write`/`SET default_transaction_read_only=off`; it is not a security boundary ([Katz](https://jkatz05.com/post/postgres/postgres-read-only/)) | `RESET` | Fly.io post-migration: the database was left read-only after cutover ([PagerTree](https://pagertree.com/blog/fly.io-migrate-to-v2-postgres-stuck-in-read-only-mode)) |
| PG `ALTER SYSTEM SET default_transaction_read_only = on` + `pg_reload_conf()` | **Yes**, for the next transaction of every session, after its current command ([config-setting](https://www.postgresql.org/docs/current/config-setting.html)) | an open transaction (incl. `idle in transaction`) keeps writing until it ends | a session/role/database-level override beats it; the app can `SET` it off; needs superuser or `GRANT ALTER SYSTEM` (not on most managed services) | `ALTER SYSTEM RESET` + reload | carried by a physical copy in `postgresql.auto.conf` |
| PG revoke write grants (migkit `freeze.py` on the target) | yes, next statement | the statement in progress finishes | table owners (can re-grant), inherited privileges, `PUBLIC` | grants back from the record | none new; owners need the role setting + session kill |
| PG revoke `LOGIN` + terminate app backends (Instacart ZDC, GOV.UK Notify) | kills them | rolled back by the terminate | superusers, migkit's own role | `ALTER ROLE ... LOGIN` | pool reconnect storms; must also kill `idle in transaction` sessions; Notify also changed the password so reconnects failed on auth ([GDS](https://gds.blog.gov.uk/2024/01/17/how-we-migrated-our-postgresql-database-with-11-seconds-downtime/)) |
| MySQL `SET GLOBAL super_read_only = ON` | yes, immediate for existing sessions ([WL#6799](https://dev.mysql.com/worklog/task/?id=6799)) | acquires the global read lock; commits are refused while it is on; the 5.1-era "blocks until pending transactions end" was changed by bug #46673 (it no longer waits on idle open transactions; their COMMIT fails) ([bug 11733](https://bugs.mysql.com/bug.php?id=11733)) | replication applier threads; XA commands were reported to still run under `super_read_only` (MySQL bug #91646, 2018; fix unconfirmed), so XA COMMIT of an already prepared XA may get through | `SET GLOBAL super_read_only=OFF` (8.0.26+ restarts the event scheduler) | server-wide, so wrong for a per-database hop (migkit measured); a long statement holding locks delays the GRL, and while `SET` waits, **all** new transactions queue behind it |
| MySQL `FLUSH TABLES WITH READ LOCK` then `read_only` | yes | waits for running statements; blocks behind any long query, and everything queues behind it | nobody | `UNLOCK TABLES` | the classic stall: FTWRL behind one long SELECT freezes the whole server |
| MySQL revoke + `KILL` (migkit `freeze.py` target path) | table-level: next statement; db-level: only after the session re-selects the db (migkit measured), hence the KILL | killed = rolled back | server-wide and role grants (named, not touched) | grants back | as above |
| MongoDB `setUserWriteBlockMode {global: true}` (6.0+) | yes, all user writes cluster-wide ([doc](https://www.mongodb.com/docs/manual/reference/command/setUserWriteBlockMode/)) | the docs do not say it waits for in-progress writes or transactions | any user with `bypassWriteBlockingMode`; the built-in `restore` role carries it ([forum](https://www.mongodb.com/community/forums/t/setuserwriteblocking-in-mongosync/286138)) | `global: false` | a replica set rejects a second call with a different `reason`; mongosync crashing mid-commit leaves the source blocked until someone unblocks it by hand |
| MongoDB `fsyncLock` | yes | blocks all writes incl. internal | nobody | `fsyncUnlock` | meant for backups; blocks the oplog too, so a change stream tail cannot drain past it |
| SQL Server `ALTER DATABASE ... SET READ_ONLY WITH ROLLBACK IMMEDIATE` | yes, ends them | rolled back | nobody | `SET READ_WRITE` | exclusive database lock, kills everything incl. readers |

Finding for migkit from this table: **no single database switch is a
complete freeze on PostgreSQL.** The combination that is complete is
`ALTER SYSTEM`/role setting for new transactions, plus revoking write
grants or `LOGIN`, plus terminating every backend whose `xact_start`
predates the freeze (idle-in-transaction included), then proving it
(section 4). On MySQL, `super_read_only` is complete for the server but
cannot be scoped; for a per-database hop, revoke + KILL (what migkit does
on the target) is the scoped equivalent. On MongoDB,
`setUserWriteBlockMode` is complete except for roles with
`bypassWriteBlockingMode`, which migkit must list before it trusts it.

### 2.2 In the pooler or proxy (writes queue instead of failing)

| Method | Behaviour | Failure modes |
|---|---|---|
| PgBouncer `PAUSE [db]` / `RESUME` | Waits for each server connection to be released per pool mode: transaction mode waits for the transaction to finish, **session mode waits for the client to disconnect**; new client queries wait in the pooler ([usage](https://www.pgbouncer.org/usage.html)). `DISABLE db` rejects new clients; `RECONNECT` recycles server connections; `KILL` drops at once | PAUSE does not return while any transaction is open: one long transaction turns seconds into minutes. `RESUME` issued concurrently with `PAUSE` can hang PAUSE forever ([#715](https://github.com/pgbouncer/pgbouncer/issues/715)). Queued clients hit `query_wait_timeout` (default 120 s). GitLab bounds it: if lag is not 0 bytes within `pgbouncer_pool_pause_zero_lag_check_timeout` (60 s) it RESUMEs on the old primary and stops ([runbook](https://gitlab.com/gitlab-com/gl-infra/db-migration/-/tree/rh/fix-multi-slot_default_readme/pg-upgrade-logical)). Also: queueing on unrelated databases after pause/resume ([#1145](https://github.com/pgbouncer/pgbouncer/issues/1145)) |
| PgCat `PAUSE db,user` / `RESUME` | per pool; bare `PAUSE` for all pools added by PR #566 ([PR](https://github.com/postgresml/pgcat/pull/566)) | open issue that PAUSE should wait for active transactions like PgBouncer's ([#917](https://github.com/postgresml/pgcat/issues/917)): i.e. it may not drain in-flight work |
| Odyssey | no PAUSE/RESUME (open request [#32](https://github.com/yandex/odyssey/issues/32)) | freeze must be done in the database |
| ProxySQL `OFFLINE_SOFT` | no new connections to that backend; in-use ones finish their work | with multiplexing disabled (session variables, temp tables, `LAST_INSERT_ID`, open transaction) the connection **stays on the OFFLINE_SOFT node and keeps getting queries**; users saw sysbench TPS not drop ([docs](https://proxysql.com/documentation/multiplexing/), [thread](https://groups.google.com/g/proxysql/c/osb7myIf4oA)). ProxySQL's PG failover primer measured a planned switch at median 1.1 s, zero errors ([blog](https://proxysql.com/blog/proxysql-postgresql-failover-primer/)) |
| ProxySQL query rule with `error_msg` | matching queries fail fast with a message | regex must be verified by `stats_mysql_query_rules` hits; rule ordering by `rule_id` |
| HAProxy `set server be/x state drain` / `maint`, `shutdown sessions server` | drain: no new sessions, existing finish; maint: immediate | existing TCP sessions never move; `shutdown sessions` in TCP mode worked only some of the time ([#2918](https://github.com/haproxy/haproxy/issues/2918)); a reload loses runtime state unless a server-state file is used (GitLab hit this) |
| RDS Proxy (in Blue/Green) | proxy keeps routing to blue while blue is read-only, then to green; existing connections are dropped at promotion ([AWS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/blue-green-deployments-switching.html)) | MySQL clients get 1290 read-only errors in the window; PG clients get `AdminShutdown` |

A pooler freeze gives the best user experience (writes wait, they do not
fail) but proves nothing about the database: an application or job that
reaches the database without the pooler keeps writing. So a pooler pause is
an *outage-shortener* layered on top of a database-level freeze, never a
replacement for it.

### 2.3 In the application

Shopify's shop mover takes the writer side of a Redis-backed
multi-reader/single-writer lock that every shop-scoped request and job
must hold as a reader ([Shopify](https://shopify.engineering/mysql-database-shard-balancing-terabyte-scale)).
Stripe raises a version number stored on the source shard; the shard then
rejects any write whose proxy-attached token is older ("stale version"),
which fences even proxies whose routing view is late ([Stripe](https://stripe.dev/blog/how-stripes-document-databases-supported-99.999-uptime-with-zero-downtime-data-migrations)).
Both are stronger than any database switch because they are enforced on
the write path itself, and both need the application's cooperation, which
a general tool cannot assume. migkit can offer a hook, not the lock.

## 3. Traffic switch: how the application gets to the target

| Mechanism | How it works | Traps |
|---|---|---|
| DNS record (CNAME/weighted) | change the name, wait out the TTL | JVMs cache per `networkaddress.cache.ttl` (forever with a security manager, 30 s otherwise; AWS recommends <= 60 s) ([AWS SDK](https://docs.aws.amazon.com/sdk-for-java/v1/developer-guide/jvm-ttl-dns.html)); **pooled connections never re-resolve**: HikariCP keeps the old IP until `maxLifetime` ([#358](https://github.com/brettwooldridge/HikariCP/issues/358)); akka-http pools never re-resolve ([#20690](https://github.com/akka/akka-core/issues/20690)); CoreDNS, the OS and the pooler each cache too. | Connection string / secret rotation | redeploy or re-read config | rollout time is the outage (GOV.UK Notify measured 5 min per redeploy and chose DNS instead); a half-rolled-out fleet writes to both sides |
| Pooler repoint (PgBouncer `RELOAD` with new host, PgCat config, ProxySQL hostgroup) | clients stay connected to the pooler; only server connections change | the pooler must be paused around it; stale server connections opened before the change must be checked with `SHOW SERVERS` |
| Service mesh / L4 proxy | route at the proxy | the same stale-TCP-session problem as HAProxy |
| Vitess `SwitchTraffic` | reads first (replica/rdonly), then writes: stop writes on source primaries (denied tables + query buffering in VTGate), wait for VReplication to reach the stop position within `--timeout` (30 s default), create the `_reverse` workflow, switch routing rules; refuses up front if lag > `--max-replication-lag-allowed` (30 s); `--dry-run` lists every step ([docs](https://vitess.io/docs/25.0/reference/programs/vtctldclient/vtctldclient_movetables/vtctldclient_movetables_switchtraffic/)) | leftover denied-table records from an earlier workflow reject queries ("enforce denied tables"); `--force` skips failed tablet refreshes |

| DataStax ZDM proxy | Phase 1 dual writes (both clusters, each at the client's consistency level), Phase 3 optional **async dual reads** on the target for comparison, Phase 4 reads from target while still dual-writing, Phase 5 clients connect directly to target ([docs](https://docs.datastax.com/en/data-migration/introduction.html)) | after Phase 5 there is no rollback without a full reverse migration; LWT `applied` flag only from the primary cluster |
| mongosync `/commit` | check `canCommit` and `lagTimeSeconds` near 0; stop source writes; `/commit`; with `enableUserWriteBlocking: sourceAndDestination` the source is blocked after commit and the destination unblocked just before `canWrite: true`; `COMMITTED` comes later once `prepareUnique` indexes become unique ([docs](https://www.mongodb.com/docs/mongosync/v1.19/reference/cutover-process/)) | the `canWrite` to `COMMITTED` gap can be long on large collections; crash mid-commit leaves the source write-blocked; dual blocking must be chosen at `/start` |
| AWS RDS/Aurora Blue/Green switchover | guardrails (replication health, lag within the timeout, no active writes on green, no long-running writes or DDL on blue, no unsupported PG changes: DDL, large objects), then stop writes on both, drop connections, wait for catch-up, rename endpoints, allow writes; timeout 30-3600 s (default 300) rolls back if exceeded ([AWS](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/blue-green-deployments-switching.html)) | the old blue stays read-only until `read_only`/`default_transaction_read_only` is set to 0 and rebooted; an app that overrides `default_transaction_read_only` at session level can write to green during switchover and those writes are lost on rollback; no reverse replication; external replicas must be re-pointed by hand |
| Google DMS `promote` | stop writes, wait for replication delay 0, promote; cannot be undone; can be promoted early at the cost of accuracy ([docs](https://docs.cloud.google.com/database-migration/docs/postgres/promote-migration)) | sequence state may differ from the source (known limitation); backups reset to defaults; pglogical left on the source |
| Azure migration service cutover | wait for "latency 0 or close"; cutover applies everything up to that point ([docs](https://learn.microsoft.com/en-us/azure/postgresql/migrate/migration-service/tutorial-migration-service-iaas-online)) | cutover with non-zero latency stretches the outage by the backlog |

The switch that costs the least outage is the one where clients are
already connected to something migkit does not have to wait for: a pooler
repoint (seconds), then DNS with a tiny TTL and forced pool eviction
(GOV.UK Notify: 11 s total, 1 s TTL), then redeploys (minutes).

## 4. The drain proof: "the last source write is on the target"

The freeze makes the source stop moving; the drain proof shows the target
has everything up to where it stopped. It has three parts and all three
must hold:

1. **Take the position after the freeze, from the source.** A position
   captured before the freeze can pass while later commits are still in
   flight. The position must include every acknowledged commit:
   * PostgreSQL: `pg_current_wal_insert_lsn()`, **not** `pg_current_wal_lsn()`.
     With `synchronous_commit = off` a commit is acknowledged when its
     record is inserted; the write position can still be behind it for up
     to 3 x `wal_writer_delay` ([WAL config](https://www.postgresql.org/docs/current/runtime-config-wal.html),
     [functions](https://www.postgresql.org/docs/current/functions-admin.html)).
     Logical walsenders decode only to the flush pointer, so the wait will
     pass once the WAL writer flushes. migkit reads `pg_current_wal_lsn()`
     (see the findings at the end of this section): fine while the
     application is writing and a later write moves the LSN on, but at a
     freeze the last async commit can sit past it.
   * MySQL: `@@global.gtid_executed` after `super_read_only`/revoke+KILL.
     Prepared XA transactions are in the binlog at PREPARE with one GTID
     and at COMMIT with a second ([XA states](https://dev.mysql.com/doc/refman/8.4/en/xa-states.html)):
     `XA RECOVER` must be empty first, or the fence passes with a
     transaction still to commit.
   * MongoDB: the source's `operationTime` after `setUserWriteBlockMode`;
     mongosync exposes the same thing as `lagTimeSeconds`/`canCommit`.
   * Kafka: the high watermark per partition after producers stop.
2. **Nothing is left open on the source.** PostgreSQL: no backend with
   `xact_start` before the freeze, and `pg_prepared_xacts` empty (an
   orphaned prepared transaction survives terminate, restart and every
   timeout, and blocks new slot creation; [The Build](https://thebuild.com/blog/all-your-gucs-in-a-row-max_prepared_transactions/)).
   MySQL: `information_schema.innodb_trx` empty for application accounts,
   `XA RECOVER` empty. MongoDB: `currentOp` shows no open transactions.
3. **The consumer has applied (not merely received) past the position.**
   PostgreSQL: `confirmed_flush_lsn` of the slot (what migkit reads; a
   native subscriber reports flush only after its commit is flushed
   locally) or migkit's own tail's saved position. MySQL:
   `WAIT_FOR_EXECUTED_GTID_SET` on the target (what migkit does). Mongo:
   the cluster time in the tail's saved token (what migkit does).

Two cheaper forms of the same proof used in production:
* **Marker row** (Instacart ZDC, GOV.UK Notify): write one row on the
  source after the freeze through a privileged account and wait for it on
  the target ([Instacart](https://company.instacart.com/how-its-made/zero-downtime-postgresql-cutovers)).
  Proves ordering end-to-end through whatever pipeline is in between, even
  one that shows no position. It is migkit's `migkit_origin` table idea,
  used as a fence.
* **Server-side wait** (GitHub): read the last executed GTID on the old
  primary after read-only, poll the new primary until it has it, stop
  replication ([GitHub](https://github.blog/engineering/infrastructure/partitioning-githubs-relational-databases-scale/)).

A position-based proof is exact; the marker row is universal. migkit
should use the position where the engine gives one and the marker row
where it does not (SQL Server today, third-party pipelines, cross-engine
through Kafka), and say in the verdict which it used.

Two findings from reading migkit's PostgreSQL fence against this:
* `src_lsn()` (`engines/postgres.py` ~6664) is the fence position `check`
  waits on, and it is `pg_current_wal_lsn()`. Per part 1 of section 4, at a
  freeze it should be `pg_current_wal_insert_lsn()`.
* `fence_wait` takes `min(confirmed_flush_lsn)` over slots that are
  **active**. If the hop's own slot is momentarily inactive (tail
  reconnecting, subscription disabled) while another consumer's slot (a
  Debezium connector, a managed service) is active and caught up, the
  fence passes on the other consumer's position, which says nothing about
  this target. At cutover the fence must include the hop's own slot by
  name, active or not. Needs a docker measurement before a fix.

| AWS Blue/Green | RDS/Aurora | stop writes both sides, drop connections | endpoint rename | docs: "typically takes under a minute"; Jan 2026: "typically five seconds or lower" single-Region, two seconds or lower with the AWS Advanced JDBC Driver ([AWS](https://aws.amazon.com/about-aws/whats-new/2026/01/amazon-rds-blue-green-deployments-reduces-downtime)); bounded by the 30-3600 s timeout that rolls back |
| Vitess | MoveTables/Reshard | denied tables + VTGate buffering | routing rules | "a few seconds"; buffering hides it from clients |
| Zalando | no public migration-cutover number found; their published logical replication work is CDC (Debezium, pgjdbc WAL growth) | | | n/a |

What these have in common, and what separates the milliseconds from the
minutes:
1. Cut over only when lag is already under a second (GitHub, Vitess
   `--max-replication-lag-allowed`, mongosync `lagTimeSeconds`, Blue/Green
   guardrail). The outage is dominated by the backlog at freeze time.
2. Clients already sit behind something that can queue or reject writes
   (ProxySQL, PgBouncer, VTGate, Stripe's proxies). DNS-based switches
   land at ~10 s, redeploys at minutes.
3. A scripted, rehearsed sequence with an automatic undo on any step
   failing (Instacart, GitLab, Blue/Green timeout, GOV.UK's 40 runs).
4. Every published zero-loss rollback has reverse replication started
   *before* traffic moves (Notion, Instacart, Vitess, PlanetScale, Stripe,
   GitLab PG16). Where it was missing (GitLab PG14) the team wrote down
   "point of no return".

## 6. Sequences, identity and auto-increment

| Engine | What replication does with counters | Documented traps | Correct move at cutover |
|---|---|---|---|
| PostgreSQL, logical (<= 18) | not replicated at all; rows carry their ids, the sequence stays at its start on the subscriber ([restrictions](https://www.postgresql.org/docs/current/logical-replication-restrictions.html)) | first insert after the flip collides (Gadget, Neon, Google DMS "known limitation") | after the drain: `setval(seq, GREATEST(source last_value, target max(col)))`, what migkit does. `pg_sequences.last_value` already covers values cached by sessions (the block end is what is logged), so it is a safe upper bound; it is NULL when never called or unreadable |
| PostgreSQL 19 | `FOR ALL SEQUENCES` publication plus `ALTER SUBSCRIPTION ... REFRESH SEQUENCES`: synced only at those moments, not continuously ([docs 29.7](https://www.postgresql.org/docs/19/logical-replication-sequences.html)) | must be run inside the window after the drain; reported (fork issue, unconfirmed upstream) to silently move a sequence **backwards** when the subscriber is ahead ([issue](https://github.com/NikolayS/postgres/issues/94)) | wrap it where both sides are 19, but keep migkit's "only ever raise" rule on top |
| PostgreSQL, physical | logged every 32 `nextval` (`SEQ_LOG_VALS`), so a standby is up to 32 (+ cache) ahead ([Red Hat](https://access.redhat.com/solutions/7082735)) | a gap, never a collision | nothing |
| PostgreSQL `CACHE n` | each session takes a block | gaps and out-of-order ids across sessions ([Cybertec](https://www.cybertec-postgresql.com/en/gaps-in-sequences-postgresql/)) | read `last_value` after sessions are terminated |
| MySQL/InnoDB | row-based replication carries explicit ids; the replica's counter follows max(id)+1 | a source whose top rows were deleted has a counter above max(id)+1: the target would hand out ids the source already used and deleted (collides with anything outside the table that kept them) | raise the target's `AUTO_INCREMENT` to the source's, read with `information_schema_stats_expiry = 0` (migkit does, `fresh=True`) |
| MongoDB | no server-side counters; app counters are documents | none at the server | nothing |
| SQL Server | `IDENTITY` and `SEQUENCE` (CACHE 50 default) | gaps after unclean shutdown | `DBCC CHECKIDENT ... RESEED` / `ALTER SEQUENCE ... RESTART` past source |
| Oracle (GoldenGate) | sequences not replicated unless configured | cached (CACHE 20) gaps | set target past source |

Buffers seen in practice: Instacart sets target = source + 1, Gadget
source + 1000, migkit exact with an opt-in buffer ("it hides that the leg
was not quiet"). With a proven freeze and drain, exact is correct; a
buffer only earns its gap as **keys apart** for the reverse leg (section
11).

**Rollback gap found in migkit:** `rollback` restores the *target's*
counters from `dst-sequences.txt`/`dst-autoinc.txt`. After a flip with
`reverse: at_cutover`, going back means the *old source* becomes primary
again; the reverse stream carries rows, not counters, so the old source's
sequences are behind every row written on the new primary. The first
insert after a rollback collides. Rollback must run the sequence sync in
the reverse direction (the reversed hop's `sync --kind sequences`) after
draining the reverse leg.

## 7. Triggers, jobs, event schedulers: exactly one side at a time

| Thing | During the move | At the flip | Failure mode |
|---|---|---|---|
| PG row triggers on the target | the native apply worker runs with `session_replication_role = replica`, so ordinary triggers **and foreign-key checks** do not fire; the initial table sync (COPY) **does** fire row and statement triggers ([architecture](https://www.postgresql.org/docs/current/logical-replication-architecture.html)); migkit loads as replica and refuses where it cannot | ordinary triggers fire for application writes: correct | `ENABLE ALWAYS` triggers fire twice (source effect replicated + target fires); FK orphans never checked (migkit has `_fk_orphans`) |
| MySQL triggers | row-based replication does not fire replica triggers; migkit takes them off for its own load and tail and records it (`set_aside`) | must be back on and verified before the flip | a trigger left off after cutover is silent corruption; `set_aside` must be empty or the flip is refused |
| pg_cron | `cron.job` is a table, so it arrives with a dump; pg_cron does not run on a hot standby but **does run on a logical subscriber**, which is a normal primary ([pg_cron](https://github.com/citusdata/pg_cron)) | `cron.alter_job(id, active := true)` on target, `false` on source | jobs fire on the target before cutover and modify rows; on the old source after the flip they write into the reverse leg's subscriber (split brain) |
| MySQL events | a native replica marks replicated events `SLAVESIDE_DISABLED` (`REPLICA_SIDE_DISABLED` in 8.4) ([MySQL](https://dev.mysql.com/doc/refman/8.4/en/replication-features-invoked.html)); with a copied schema they carry whatever status the dump had | `ALTER EVENT ... ENABLE` on target (the runner becomes the definer), `DISABLE ON REPLICA` on the old source; 8.0.26+ restarts the scheduler when `super_read_only` goes off | events stay disabled after promotion (bug #108421 for Group Replication); events run on both sides |
| SQL Server Agent / Oracle `DBMS_SCHEDULER` | outside the database copy (Agent in `msdb`) or copied with the schema | enable on target, disable on source | same double-run |
| Application jobs, queue workers, outbox relays | outside migkit; `watch` names tables still HOT | stopped or repointed with the app | the classic "the source is still being written after the app was stopped" |
| Downstream CDC on the source (Debezium, a managed task) | their slots sit on the source; migkit's PG fence already waits for every active slot | stop the connector after it passed the final position, **create its slot on the new primary before writes resume**, reset its offsets (new LSN space), keep the topic prefix ([Debezium](https://debezium.io/documentation/reference/stable/connectors/postgresql.html), [AWS](https://aws.amazon.com/blogs/database/migrate-amazon-aurora-postgresql-across-major-versions-with-active-debezium-cdc-connectors-using-native-logical-replication/)) | a slot created after writes resume skips them silently; an old offset on a new cluster skips or replays; downstream LSN watermarks drop valid events |

migkit can inventory every row of this table from the catalogues on both
sides (pg_cron's `cron.job`, `information_schema.events`, `msdb.dbo.sysjobs`,
`dba_scheduler_jobs`, `pg_trigger.tgenabled`, `pg_replication_slots` not
owned by the hop) and say before the window which side each is enabled on.

## 8. Caches

* Application caches keyed by row id stay correct across a cutover whose
  drain is proven, because the data is identical at the flip.
* **Invalidation fed by CDC from the source** (a Debezium-to-cache
  invalidator, a search indexer) stops at the flip unless that consumer
  moves with it (section 7). This is the cache failure that actually
  happens: not stale data at the flip, but no invalidations after it.
* Caches filled from the **target's reads before the flip** (reads switched
  early, Vitess/PlanetScale/Instacart-style) hold values up to the lag
  old. Bump the cache key namespace at the flip, or keep read-switching
  only where the application already tolerates replica lag.
* Pooler-side state (server prepared statements, `SET`s) is dropped with
  the server connections; the pooler must be recycled (`RECONNECT`) after
  the repoint.
* Database-side caches (plans, statistics) are a performance risk, not a
  correctness one: `ANALYZE` before the flip (Google DMS and AWS Blue/Green
  both say so; migkit already analyzes in stages after a load).

## 9. Long-running and prepared transactions

* **They set the freeze's length.** PgBouncer `PAUSE` does not return
  while one transaction is open; ProxySQL keeps routing a non-multiplexed
  connection to an OFFLINE_SOFT node; FTWRL and `read_only` queue every new
  transaction behind one long statement; AWS Blue/Green refuses to start
  on "long-running active writes" and "long-running DDL". So the check
  belongs **before** the freeze: refuse to start while a write
  transaction older than the budget exists, instead of freezing and then
  waiting.
* **Terminate rolls back; that is safe.** A transaction killed by the
  freeze never committed, so it is not a data problem, only an error the
  application must retry. It must be killed, though: a PG session whose
  transaction started before `ALTER SYSTEM ... read_only` keeps writing.
* **Prepared transactions are different: they survive.** A PG
  `PREPARE TRANSACTION` survives terminate, restart and every timeout
  (`idle_in_transaction_session_timeout`, and PG 17's `transaction_timeout`
  stops counting at PREPARE); it blocks logical slot creation ("waiting
  for transactions older than ... to end"), which is exactly what the
  reverse leg does at the flip ([The Build](https://thebuild.com/blog/all-your-gucs-in-a-row-max_prepared_transactions/)).
  MySQL XA: PREPARE and COMMIT are two GTIDs, the prepared one holds locks
  and the purge view, it replicates to replicas, and a killed XA COMMIT
  under a global read lock lost the prepared transaction in bug #84539
  ([Percona](https://www.percona.com/blog/how-to-deal-with-xa-transactions-recovery/)).
  Both must be empty on **both** sides before the freeze
  (`pg_prepared_xacts`, `XA RECOVER CONVERT XID`), and the check has to
  run on the primary: a hot standby's `pg_prepared_xacts` reads empty.
* MongoDB bounds multi-document transactions by
  `transactionLifetimeLimitSeconds` (60 s by default), so a freeze waits
  at most that long; whether `setUserWriteBlockMode` waits for open
  transactions is not documented and needs measuring.

## 10. DDL during the window

* PostgreSQL's logical replication does not replicate DDL; a column added
  on the source stops the apply worker with "target relation is missing
  replicated column" ([Bytebase](https://www.bytebase.com/reference/postgres/error/logical-replication-target-relation-missing-replicated-columns/)).
  Additive changes go to the subscriber first, destructive ones to the
  publisher first; NOT NULL without a default breaks it even when run on
  both (bug #15549). AWS Blue/Green degrades replication and refuses the
  switchover after any DDL or large-object change on blue. GitLab freezes
  deployments for the whole window because migrations are DDL.
* MySQL's binlog carries DDL; migkit's own tail stops on a schema change
  rather than carrying half of it.
* MongoDB change streams carry DDL events (`create`, `drop`, `rename`,
  and more with `showExpandedEvents`).
* **The rollback window is also a DDL freeze:** DDL on the new primary
  breaks the reverse leg the same way ("you cannot run any DDL statements
  on the database after that", Laurenz Albe on reverse logical
  replication, on the pgsql-general list).
* For migkit: compare the schema shape (`drift.shape`) of both sides at
  the fence, and refuse the flip on any difference the hop's mapping does
  not explain; keep comparing it on the reversed hop for the rollback
  window and say so as soon as the new primary's schema moves.

## 11. The reverse leg and rollback

**Every published zero-loss rollback starts reverse replication before
traffic moves** (Notion, Instacart, Vitess `_reverse`, PlanetScale primary
mode, Stripe's origin-tagged bidirectional replication, GitLab from PG16).
Where it was missing, the team called the flip "point of no return"
(GitLab PG12 to 14), and ZDM says the same after Phase 5.

Making the reverse leg safe:
1. **Position:** it starts at the flip, before any application write on
   the new primary. Debezium's rule is the same one: "create the slot
   before enabling writes". migkit already gives the target back only once
   the stream back runs (`_replicate_released`).
2. **No loops:** PG 16+ `origin = none` on both subscriptions, with
   `copy_data = false` because the initial copy is not origin-filtered
   ([CREATE SUBSCRIPTION](https://www.postgresql.org/docs/current/sql-createsubscription.html));
   MySQL: unique `server_id`, `replicate_same_server_id = 0`, GTID
   auto-position, and the forward channel stopped and `RESET REPLICA ALL`
   before the reverse starts; MariaDB `@@skip_replication` with
   `replicate_events_marked_for_skip`; MySQL 8.3+ tagged GTIDs label but
   have no replica-side tag filter (a `gtid_purged` workaround only)
   ([Mydbops](https://www.mydbops.com/blog/simplifying-replication-with-tagged-gtid-in-mysql-8-4)).
   migkit's own tails use `migkit_origin` (`twoway.py`) where no tag
   exists.
3. **One writer:** the old source stays frozen for the application's
   roles (only the reverse applier writes), set persistently (`SET
   PERSIST super_read_only` on MySQL, so a restart cannot make it
   writable). An application write on the old source after the flip is
   split brain; the freeze makes it an error instead.
4. **Keys apart (optional):** start the new primary's sequences a margin
   above the source's, or stagger `auto_increment_increment/offset`. A
   stray write on the old source then cannot collide with a row the
   reverse leg brings back, and any id in the margin found on the old side
   is evidence of a split-brain write. Costs a visible gap; off by default,
   chosen per hop.
5. **Version direction:** MySQL does not support replication from a newer
   major version to an older one; a reverse leg of an upgrade is outside
   support, and migkit must say so up front.
6. **Verified before the target is thawed:** "An unverified reverse
   channel is not a rollback plan." Write a marker on the new primary with
   migkit's own account and see it on the old source before giving the
   application its writes.
7. **Counters on the way back** (section 6 gap): rollback syncs sequences
   onto the old source after draining the reverse leg.

**Rollback criteria, written before the window** (the sources agree on
the shape, not the numbers): a named decider and a deadline; numbers for
error rate and p99 against the pre-cutover baseline (examples in the
wild: error rate > 1-2 % for 5-15 min, p99 > 2-3x baseline), reverse-leg
lag bound, and "fenced verify shows any difference" as an automatic stop.
The rollback itself is a cutover in the other direction: freeze the new
primary, drain the reverse leg to a fence, sync counters onto the old
source, flip back.

**Point of no return** = the moment the reverse leg stops (PlanetScale
"Complete", ZDM Phase 5). migkit should make that a separate, explicit,
approved step with its own record, never a side effect.

## 12. Rehearsal

* GOV.UK Notify ran its cutover script "at least 40 times" before the 11 s
  production run; GitLab rehearsed every step on production copies ("the
  only step not tested was the switchover"); Vitess and Blue/Green both
  offer a dry run that walks every step and checks it can finish inside
  the timeout; Ghostferry's docs tell you to time verification on a
  staging move; practitioners: "the timing from a rehearsal is your real
  cutover window".
* What a rehearsal must record to be useful for the real one: time per
  phase, backlog at freeze and drain rate, sessions killed, the longest
  transaction seen, sequences moved, reverse-leg start time and first
  marker round trip. migkit already refuses to estimate a move without a
  rehearsal; the cutover should do the same for its outage.

## 13. Verifying after the flip that the application sees the same data

* **Before the flip, with the application's help:** shadow or dark reads.
  Notion compared old and new with a 1 s delay and matched "nearly 100 %";
  ZDM's async dual reads send reads to the target and only log the
  results; GitHub's Scientist standard is zero mismatches with no ignore
  blocks ([Scientist](https://github.com/github/scientist)). migkit cannot
  do this for an application, but it can supply the comparison for the
  keys an application logs.
* **At the flip, without it:** migkit's fenced, confirm-pass `check`. Keep
  the expensive part outside the window: `watch --verify --delta`
  (O(changes)) runs up to the freeze, so inside the window only the rows
  changed since the last verified cycle are compared. Ghostferry shows
  the cost of doing it the other way: verification inside the cutover
  adds straight to downtime.
* **After the flip:** with the reverse leg running, the old source is a
  follower, and `check` on the reversed hop keeps proving the two are the
  same. A difference there means a writer on the old side or a broken
  reverse leg, both rollback triggers.
* **Read-your-writes across the switch:** switching reads before writes
  (Vitess, PlanetScale, Instacart moved replicas first) serves reads that
  are up to the lag stale; the old side's read replicas must stop serving
  at the write flip, or be fed by the reverse leg. PG 19's `WAIT FOR LSN`
  and MongoDB causal consistency are the database-side tools for
  read-your-writes on replicas ([Pachot](https://dev.to/franckpachot/read-your-writes-on-replicas-postgresql-wait-for-lsn-and-mongodb-causal-consistency-4he2)).
* **A canary through the application path:** one write and read through
  the application after the flip proves the switch, not just the data.

## 14. Design: migkit's cutover as one command path

### 14.1 Shape, inside the existing rules

* **No new verb, mode or flag.** The cutover already *is*
  `migkit move HOP --mode cdc --drop --go` (tearing the stream down,
  approvals step `cutover`, `reverse: at_cutover`, `protect_target` thaw).
  Without `--go` it prints the plan and the predicted outage, as `move`
  already does. Going back stays `migkit rollback HOP ... --apply`, which
  runs the same path on the reversed hop.
* **Hop options only**, all optional, a hop without them behaves as today:

```yaml
options:
  protect_target: true          # exists
  reverse: at_cutover           # exists
  cutover:
    budget: 30                  # seconds of write outage; exceeded = automatic undo
    start_below: 1              # seconds of lag (from the fence distance) to allow the freeze
    freeze: auto                # auto | database | pooler+database | operator
    pooler: {kind: pgbouncer, admin: <address from the hop's secrets>, databases: [app]}
    flip: <command>             # run at the flip (DNS/pooler reload/config push); none = print it
    keys: exact                 # exact | apart:<margin>
    jobs: move                  # move = enable on target, disable on source; leave = report only
```

* **"migkit never writes to a source"**: the freeze, a marker row, turning
  jobs off and the reverse leg all write to the source. They run only when
  the hop opts in (`cutover.freeze` other than `operator`, `reverse`,
  `jobs: move`), the same exception `reverse: at_cutover` already makes.
  With `freeze: operator` migkit writes nothing to the source: it waits for
  the operator's stop and **proves** it (no application sessions, no open
  or prepared transactions, the tail's last applied commit time older than
  the stop) before it goes on.

### 14.2 The phases, each with a gate, a clock and an undo

Failpoints `cutover.<phase>` (existing `failpoint.py`) sit between every
phase, and the state of each phase is written before it acts, so a kill at
any point is resumed or undone by the next run, never left half-flipped.

| # | Phase | In the outage? | Gate (all must pass) | Undo |
|---|---|---|---|---|
| 0 | **Preflight** | no | capability matrix for the pair; lag below `start_below`; no write transaction older than the budget; `pg_prepared_xacts` / `XA RECOVER` empty on both sides; schema shape equal (`drift.shape`); `set_aside` empty (triggers back); `protect_target` active; the reverse leg possible (`loops_prevented`, version direction, slots/`wal_level`/`server_id`); roles able to bypass the freeze named (superuser, `bypassWriteBlockingMode`, server-wide grants); jobs and events inventory with the side each is on; other consumers' slots named; approvals signed; predicted outage from the rehearsal's measured rates <= budget | nothing to undo |
| 0b | **Pre-arm** | no | reverse leg created paused where it is loop-safe before the flip: PG 16+ both sides with `origin = none`, `copy_data = false`; MySQL with GTID auto-position (the old source already holds every source GTID, so only target-originated ones would flow, and the target is frozen); final delta verify running continuously | drop it |
| 1 | **Freeze source** (clock starts) | yes | the method the decision engine picked (14.3) reports every application session ended or blocked, and the proof reads clean | thaw exactly what was recorded (grants, `ALTER SYSTEM RESET`, `RESUME`, `global: false`) |
| 2 | **Drain** | yes | position taken **after** the freeze (PG `pg_current_wal_insert_lsn()`, MySQL `gtid_executed`, Mongo `operationTime`, Redis `master_repl_offset`, Kafka high watermarks) reached by the hop's **own** consumer, by name; marker row where no position exists; wait bounded by the remaining budget | back to 1's undo |
| 3 | **Final fenced verify** | yes | confirm-pass `check` over the rows changed since the last verified cycle only (the delta loop ran up to the freeze); counts per table; shape again | back to 1's undo; a difference is never repaired inside the window by default |
| 4 | **Counters** | yes | `GREATEST(source, target max)` after the drain (exact) or plus the margin (`keys: apart`); undo written first; the source's values recorded for a later rollback | restore from the record |
| 5 | **Reverse leg live** | yes | enabled (or created, where it could not be pre-armed); a marker written on the target by migkit's account arrives on the old source; old source stays frozen for application roles, persistently | stop and drop it |
| 6 | **Jobs** | yes | with `jobs: move`: pg_cron `active`, MySQL events `ENABLE` on target, `DISABLE ON REPLICA` on the old source, Agent/Scheduler likewise; read back | reverse the toggles |
| 7 | **Flip** (clock stops) | yes | target thawed (`protect_target` release); `flip` command exits 0; pooler repointed, `RECONNECT`, `RESUME`; first application commit seen on the target | freeze target, run the flip command's undo if given, thaw source, drop reverse leg: the old source is primary again with nothing lost, because nothing was written on the target yet |
| 8 | **After** | no | reversed hop watched (`watch --verify --delta`), reverse lag, application sessions still on the old source reported (they fail: it is frozen), rollback criteria evaluated, outage and every phase's time written to the run's record | rollback = phases 1-7 on the reversed hop, with counters synced onto the old source |
| 9 | **Point of no return** | no | its own approved step: the reverse leg stopped, old source thawed or retired | none, by definition |

Undo is automatic for any failure in phases 1-7 and whenever the clock
passes `budget` (Instacart ZDC and AWS Blue/Green both do this).

### 14.3 The freeze, chosen from what the source allows

The decision layer probes, it does not ask: privileges (superuser,
`rds_superuser`, `pg_signal_backend`, `GRANT ALTER SYSTEM`,
`CONNECTION_ADMIN`/`SYSTEM_VARIABLES_ADMIN`, `setUserWriteBlockMode`),
version, whether the hop covers the whole server or cluster, whether a
pooler admin is configured, and managed-service limits (Neon cannot end
other users' sessions; Cloud SQL has no `ALTER SYSTEM`).

| Source | Layer 1 (queue, optional) | Layer 2 (the database-level freeze, always) | Proof |
|---|---|---|---|
| PostgreSQL | PgBouncer/PgCat `PAUSE db` bounded by the budget (never concurrent with `RESUME`) | whole server in scope and allowed: `ALTER SYSTEM default_transaction_read_only` + reload; otherwise per database: revoke `CONNECT` and write grants from the app roles (recorded, `freeze.py` generalised to `side=src`), role-level `default_transaction_read_only`; then terminate app backends whose `xact_start` predates the freeze; where terminate is not allowed, wait for them within the budget | no app-role backend older than the freeze; no prepared xact; the hop's slot past the insert LSN |
| MySQL / MariaDB | ProxySQL `OFFLINE_SOFT` + write `error_msg` rule | whole server in scope: `super_read_only` (`SET PERSIST` for the rollback window); otherwise revoke + `KILL` (existing `freeze.py` path) | `XA RECOVER` empty; `innodb_trx` empty for app users; `WAIT_FOR_EXECUTED_GTID_SET` / tail position |
| MongoDB | none | 6.0+, whole cluster in scope, no app user with `bypassWriteBlockingMode`: `setUserWriteBlockMode`; otherwise swap app users' roles to read-only and `killSessions` | tail token time >= `operationTime` after the block |
| Redis | none | `CLIENT PAUSE <budget ms> WRITE` (6.2+; keeps the replication offset still by design) | replica offset >= `master_repl_offset` |
| SQL Server | none | `ALTER DATABASE ... SET READ_ONLY WITH ROLLBACK IMMEDIATE` (database-scoped) | marker row until migkit has a SQL Server change stream |
| Kafka | producers stop (application) | none on the broker | high watermark per partition reached; group offsets translated (done) |
| Anything else / no privilege | none | `freeze: operator` | settle on quiet, said as such in the verdict |

### 14.4 What it guarantees, and what it does not

Guarantees, each stated in the verdict with the evidence:
1. **Nothing acknowledged on the source is missing on the target at the
   flip**: freeze proven, position taken after it at the insert
   LSN/GTID set/cluster time/offset, reached by the hop's own consumer.
   Where the engine has no position, the verdict says "marker" or
   "settled on quiet" instead of "fenced".
2. **No write lands on the target before the flip** (`protect_target`)
   **and no application write lands on the old source after it** (it stays
   frozen; the reverse applier is its only writer).
3. **The first key the target hands out is past every key the source
   used.**
4. **Going back loses nothing written after the flip** while the reverse
   leg runs and no DDL is made on the new primary (checked every cycle).
5. **Never half-flipped:** any failure or a blown budget before the flip
   returns to the source, automatically, with every change undone from its
   record.
6. **Every step recorded, approved where the hop asks, and timed.**

Not guaranteed, and said before the window: accounts that bypass the
freeze (named in preflight); side effects outside the database (mail
sent, payments called) of transactions the freeze rolled back; clients
that do not follow the flip (reported, and they fail against the frozen
old source rather than write to it); application caches fed by
invalidation from the source's CDC.

### 14.5 Outage budget achievable per engine

outage = freeze (longest open write transaction, or pooler drain)
+ drain (backlog at freeze / apply rate + consumer flush interval)
+ final delta verify + counters + reverse-leg enable (pre-armed: ~0)
+ flip (pooler reload ~ms; DNS TTL + pool eviction ~seconds; redeploy
~minutes).

| Pair | With a pooler/proxy in front, lag < 1 s at freeze | DNS switch | Evidence |
|---|---|---|---|
| PG to PG, native logical | 2-10 s | 10-15 s | Gadget 3 s, Instacart 5-10 s, Figma 10 s, GOV.UK 11 s (DNS, 1 s TTL) |
| MySQL to MySQL, native GTID | < 1-3 s | ~10 s | GitHub tens of ms, ProxySQL 1.1 s median, Blue/Green <= 5 s (2026) |
| MongoDB to MongoDB (mongosync or migkit's tail) | seconds to tens of seconds; `canWrite` to `COMMITTED` can be long but writes are allowed from `canWrite` | same | Stripe < 2 s with its own proxy fence |
| Redis to Redis | ~1 s | seconds | `FAILOVER`/`CLIENT PAUSE WRITE` design |
| Cross-engine through migkit's tail | 5-30 s, dominated by the tail's apply latency and flush interval | + DNS | to be measured |
| SQL Server source (no change stream in migkit yet) | minutes (settle) | minutes | to be closed by 0e |

These are targets to measure in docker, not promises; migkit prints its
own prediction from the rehearsal and refuses when it exceeds `budget`.

### 14.6 What to test in docker (failure injection at every step)

Every test runs a writer container that writes continuously and records,
per write, success, error or time blocked: **the outage is measured from
the client's side**, the only honest number. Faults use what docker
already has (`docker pause`, `docker network disconnect`, `kill -9` of
migkit through `MIGKIT_FAILPOINT=cutover.<phase>:1:exit`), no new tools.

1. **Freeze.** A session idle in transaction from before the freeze tries
   to commit after it (must fail or be killed). A session that sets
   `default_transaction_read_only = off`. A role that owns its tables. An
   app role with superuser or `bypassWriteBlockingMode` (preflight must
   name it). PgBouncer `PAUSE` behind a long transaction (budget undo,
   `RESUME` issued once). kill -9 right after the freeze (next run finds
   the record and resumes or thaws).
2. **Drain.** Source with `synchronous_commit = off` and a commit in the
   last milliseconds before the freeze (the insert-LSN fence must include
   it; the write-LSN one is the regression test). The hop's slot inactive
   while another slot is active and caught up (fence must not pass).
   Tail killed mid-drain. Target network disconnected (timeout, undo).
   Pipeline with no position (marker row).
3. **Open work.** PG `PREPARE TRANSACTION` and MySQL `XA PREPARE` left
   open on source, then on target (preflight refuses; reverse slot
   creation would hang).
4. **Verify.** A row changed on the target alone (abort). A change still
   arriving (confirm pass, not a diff). DDL on the source during the window
   (shape gate aborts).
5. **Counters.** `CACHE 20` sequences used by several sessions; identity
   columns; sequences owned by no column; MySQL table whose top rows were
   deleted (counter above max+1); `keys: apart` margin; rollback syncs the
   old source's counters (first insert after rollback must not collide).
6. **Reverse leg.** Pre-armed on PG 16 (`origin = none`) and MySQL GTID:
   a write on the new primary arrives once on the old source and never
   comes back; an app write on the old source is refused; slot creation
   blocked by an open transaction on the target (bounded, undo); a newer
   to older MySQL major refused in preflight.
7. **Jobs.** pg_cron job active on the target before the flip (preflight
   names it); MySQL event `REPLICA_SIDE_DISABLED` enabled at the flip;
   MySQL triggers set aside and not restored (flip refused).
8. **Flip.** Flip command fails (undo to source, nothing lost). Flip
   succeeds while a client keeps its pooled connection to the old source
   (its writes fail and `doctor` names it).
9. **Kill at every failpoint** between phases 1 and 7, with the writer
   running: the rerun either completes or returns fully to the source; a
   row count and checksum on both sides and the writer's log show no lost
   acknowledged write.
10. **Budget.** A backlog bigger than the budget (preflight refuses); a
    drain that slows down mid-window (automatic undo, outage recorded).
11. **Rollback.** Rows written on the target after the flip, then
    rollback: reverse leg fenced, counters synced onto the old source, app
    back on it, no loss, no collision.
12. **Measurement runs** per pair (PG-PG, MySQL-MySQL, Mongo-Mongo,
    Redis-Redis, MySQL-PG through the tail) with a pooler and without,
    publishing the client-side outage next to the table in 14.5.

### 14.7 Effort

| Piece | Effort |
|---|---|
| PG fence: insert LSN at freeze, the hop's own slot by name (measure first) | S |
| Preflight gates (old write transactions, prepared/XA, bypass roles, shape, set-aside, jobs and other slots inventory, outage prediction) | M |
| Source freeze per engine: `freeze.py` generalised to the source side for PG/MySQL, Mongo write block/role swap, Redis `CLIENT PAUSE WRITE`, SQL Server `READ_ONLY` | M |
| Pooler layer (PgBouncer, PgCat, ProxySQL) with bounded pause and single resume | M |
| Drain with marker fallback, and the verdict saying which proof it used | S |
| The phased path in `move --mode cdc --drop --go`: state record per phase, clock, budget, automatic undo, failpoints | L |
| Reverse leg pre-armed and verified with a marker; MySQL reverse measured; counters onto the old source at rollback | M |
| Jobs and events moved between sides | M |
| Flip hook, pooler repoint, stragglers reported by `doctor` | S |
| Docker suite of 14.6 with a client-side outage recorder | L |
| Per-pair outage measurements published | M |

Overall: **L**. Order: the two fence fixes and the rollback counters first
(each closes a way a "clean" cutover loses or collides data today), then
preflight and the source freeze, then the phased path with its undo, then
the reverse-leg pre-arm, jobs and the measurements.
