migkit's own decision engine finds the fastest, exact, consistent way for each source -> target pair, and says which it chose and why. Around the move it does what a mover leaves out: it prepares the target, follows the source's changes, proves every row and object arrived, repairs what did not with the undo kept, and cuts over with the least downtime.

Five minutes

uv tool install migkit
migkit doctor --install
migkit init
migkit assess shop
migkit move shop --mode full+cdc
migkit move shop --mode full+cdc --go
migkit check shop
migkit move shop --mode cdc --drop --go

Configure a hop

A hop in conf/hops.yaml needs only its two addresses and what it is for (goal). Passwords are kept by migkit init in the system keychain or env:MIGKIT_<HOP>_<SIDE>_PASSWORD, never in the file:

hops:
  shop:
    goal: cutover
    source: postgres://app@db1.example.com:5432/shop?sslmode=verify-full
    target: postgres://app@db2.example.com:5432/shop?sslmode=verify-full

What a hop is for (Goals)

GoalWhat it is for
copymove the data once and prove every row arrived
cutovermove, follow the source's changes, prove both equal, and switch with the least downtime - a stream back ready from the moment of the switch
verifyprove two databases hold the same; nothing is written to either
two-wayboth sides written, each side's changes carried to the other
keep-in-synca copy that follows the source for as long as it runs, the application kept off it
rehearsethe whole path the real run will take - copy, follow, prove, cut over - on a copy or a sample of the source into a target of its own, every phase timed, so the hop it rehearses (rehearses:) is forecast from what it measured
upgradethe same engine at a newer version, a higher edition (SQL Server Web to Enterprise), or both, with the least downtime: what the new version or edition changes checked first, then the data moved into it and followed, or a copy of its pages taken to the target where the hop allows it - upgraded there where the version moves - and switched over
subseta copy for testing: the rows chosen and every row they refer to, masked where the hop says, into a staging or developer database, proved row by row
consolidatemany databases or tenants into one: each source's rows under a column the hop names, filled with its own value, keys kept apart by the hop's rule, proved source by source
splitone database into many - a service extracted, a database split by region: each part's rows by its rule, every row placed exactly once, proved, and followed until every part is cut over at once
reshardN sources onto M targets by one shard function - shards split or merged, a new shard key, a cluster's own distribution - every row placed exactly once, proved, followed until every source and target is cut over at once
archiveold rows to cheaper storage: the rows each rule picks added to an archive and proved there, then removed from the source only once proved and only where the hop allows it

Execution modes (--mode)

Every move or synchronization mode shows its plan first and writes nothing until --go or --apply:

CommandWhat it does
move --mode fullone copy of every table the hop carries: the source read, the target written - kept from the application's writes before the first row and again after the last where the hop asks (protect_target): its rights taken, its access policy changed on an answer of yes, or its writes named, the way the target allows
move --mode cdcthe stream of changes started, or resumed from where it stood: the source's log read, the target written change by change
move --mode full+cdcthe copy, then the stream from a position taken before the copy began, so nothing changed during it is lost
move --mode cdc --dropthe cutover: the stream torn down, the target given back to the application where protect_target kept it, and what else happens on each side is what cutover: says (below); run again once a cutover of the hop has flipped, its point of no return
sync --mode reconcilethe last check's differences shown; --apply writes the target to match the source
sync --mode verifyread only: every table compared as of one moment
sync --mode seedthe schema aligned, the copy, the differences repaired and a consistent check, one after another
sync --mode streamthe stream started, and each cycle's changes compared
sync --mode migrateseed, then stream

Verification modes: check vs deep vs delta vs scan

Every verification mode is 100% read-only on both source and target, throttles itself automatically when server load or replication lag rises, and writes verdict.json, summary.json and report.html:

Layer / ModeCommandCost / ComplexityWhat it verifiesWhen to use
check (Full battery)migkit check shopO(all rows) in resumable key rangesRuns schema, counts, autoinc (sequences), data (injective per-row hash + adaptive Merkle / key-range drilldown), deep, and params. Row counts ride inside the checksum query so tables are not scanned twice.Post-load certification, pre-cutover sign-off, or standalone database audit (goal: verify).
deep (Semantic & catalog audit)migkit check shop --deep or migkit check shop --only deepO(1 fused scan) + catalog queriesAudits 20+ silent failure classes beyond row hashes: NULL vs '', float/NaN precision drift, charset/double-encoding, timezone shift, unvalidated (NOT VALID / NOT ENFORCED) constraints, invalid indexes, disabled triggers, FK orphans, RLS, matviews, grants, and ownership.Catching subtle cross-engine or dialect/collation corruption that row counts and naive checksums miss.
scan (Fused aggregate read plan)Automatic inside migkit check shop (scanplan)1 pass per key range (up to 512 expressions/read)Instead of scanning a billion-row table once per column for each deep/value check, scanplan fuses every aggregate expression (SUM, MIN, MAX, digest) into one shared range scan per side, falling back to isolated column reads only if an expression fails.Always active automatically during check and deep to keep database I/O and wall-clock time flat.
delta (Change-driven continuous verify)migkit watch shop --verify --delta or migkit sync shop --mode streamO(changed rows since last mark)Reads the source change stream (WAL slot, binlog, oplog, SCN/redo, or change table) and re-verifies only the primary keys touched since the last verified checkpoint. Distinguishes in-flight replication lag from real drift and announces SAFE TO CUT OVER only when diffs=0, source is quiet, and lag=0.Continuous live verification on multi-terabyte tables during CDC streaming right up to the cutover second.
sample (Time-bounded quick probe)migkit check shop --sample 10O(seconds budgeted)Sizes and reads random keys on both sides within the given time budget (e.g. 10 seconds). Reports different immediately if any sampled row mismatches, or incomplete (never a false same) until full check runs.Fast smoke check in seconds before running the full table scan.
drill (Column-by-column row diff)migkit check shop --db shop --table public.orders --drillO(limit rows)Pinpoints the exact primary keys and specific columns that differ inside one table, masking values with keyed HMAC-SHA256 when mask is configured.Inspecting exact row/column differences before running migkit sync shop --apply.

Ready-to-run verification commands (click any highlighted parameter to customize inline):

# 1. Full read-only verification (schema + counts + sequences + data + deep + params)
migkit check shop

# 2. Consistent snapshot verification across tables + deep semantic checks
migkit check shop --consistent --deep

# 3. Run only specific check layers (e.g. deep audit or data checksums only)
migkit check shop --only deep
migkit check shop --only schema,counts,data

# 4. Continuous O(changes) delta verification while the source is live
migkit watch shop --verify --delta

# 5. Drill into one table's differing columns, or export the signed evidence bundle
migkit check shop --db shop --table public.orders --drill
migkit report shop

Cutover runbook

From readiness check to fenced switchover in four commands:

migkit assess shop
migkit move shop --mode full+cdc --go
migkit check shop

Silent-corruption classes detected

Row counts (SELECT COUNT(*)) pass on every one of these failure modes. migkit check catches all 11 before cutover:

Safety

  • Every command that writes shows its plan first, starting with what each side will see, and writes nothing until --go or --apply.
  • What each goal does on the source is said before it runs: goals. No goal turns the cutover migkit drives on; a hop turns it on itself.
  • Every repair keeps its undo, and migkit rollback puts it back.
  • migkit check never writes to either side.
