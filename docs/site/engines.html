Engines

34 engines, any two of them as a pair, and what each can do.

Every engine this version has, and what it can do - read off the code, so this page claims no more and no less than it does. A hop names its two sides by their addresses; migkit's own decision engine finds the fastest, exact, consistent way for each source -> target pair, and says which it chose and why.

Each shape of table

A table without a key, a key of many columns, a table too large for one range: each shape has a way of its own on each engine, chosen by the decision engine.

  • keyless: a table without a key
  • no unique index: a table with no unique index
  • wide key: a key of many columns or of text
  • too large: a table too large for one range
  • large values: a table with large values
  • partitioned: a partitioned table
  • read-only source: a source that is read-only or a standby
  • missing grant: a user without the grant a program needs
  • read-only target: a target that must stay read-only
  • slow link: a link too slow for one stream
  • writes held: a side whose writes are held and let go again, read back - the source at cutover

Stored code carried and proved

Views, functions, procedures and triggers are converted one at a time by whichever way proves itself on each, and each version, whoever wrote it, is run on both sides in a sandbox and compared. Between any two of PostgreSQL, MySQL, SQL Server, SQLite, ClickHouse, Oracle Database, TiDB, CockroachDB, Aurora DSQL, a routine is carried by:

  • the operator's own file: view, function, procedure, trigger, event
  • the query translator: view, function
  • a model: view, function, procedure, trigger, event

Each engine

PostgreSQL

postgres, also written alloydb, aurora-postgres - either side.

It does: comparing the schema; comparing row counts; comparing the data itself; the deep checks; carrying sequences and auto-increment values; comparing server settings; moving a whole database in bulk; copying table by table, resumably; keeping the target following the source; proving the target has caught up before cutover; telling a difference still arriving from one that is wrong; verifying only what changed; carrying users and their grants; noticing a move that moved nothing; refreshing the target's statistics after a load; snapshotting the target so a cutover can be rolled back.

Db2 (Linux, UNIX, Windows)

db2 - either side.

It does: comparing the schema; comparing row counts; comparing the data itself; the deep checks; copying table by table, resumably; noticing a move that moved nothing.

Not yet:

  • carrying sequences and auto-increment values - meanwhile, set each sequence on the target above the source's highest value before cutover
  • comparing server settings - meanwhile, compare the server settings by hand
  • moving a whole database in bulk - meanwhile, move it table by table, or restore a backup of the source
  • keeping the target following the source - meanwhile, stop writes on the source, move it once, and prove it with migkit check before cutover
  • proving the target has caught up before cutover - meanwhile, stop writes on the source and let migkit check prove the target before cutover
  • telling a difference still arriving from one that is wrong - meanwhile, stop writes on the source before the final check, so nothing is still arriving when it looks
  • verifying only what changed - meanwhile, run migkit check, which compares everything rather than only what changed
  • carrying users and their grants - meanwhile, create the users and their grants on the target by hand
  • refreshing the target's statistics after a load - meanwhile, refresh the target's statistics by hand after the load
  • snapshotting the target so a cutover can be rolled back - meanwhile, take a backup of the target yourself before cutover

  • carrying users and their grants: who may use an application is the application's own, not carried
  • noticing a move that moved nothing: a SaaS application is read, never written: it is a pair's source (engine: hetero, source_engine: saas), and a hop between two of them compares them
  • refreshing the target's statistics after a load: a SaaS application is read, never written: it is a pair's source (engine: hetero, source_engine: saas), and a hop between two of them compares them
  • snapshotting the target so a cutover can be rolled back: a SaaS application is read, never written: it is a pair's source (engine: hetero, source_engine: saas), and a hop between two of them compares them

Any pair of two engines

hetero - the pair: a source of one engine, a target of another.

It does: comparing the schema; comparing row counts; comparing the data itself; the deep checks; carrying sequences and auto-increment values; comparing server settings; moving a whole database in bulk; copying table by table, resumably; keeping the target following the source; proving the target has caught up before cutover; telling a difference still arriving from one that is wrong; verifying only what changed; noticing a move that moved nothing; refreshing the target's statistics after a load; snapshotting the target so a cutover can be rolled back.

Not yet:

  • carrying users and their grants - meanwhile, create the users and their grants on the target by hand

Any other SQL engine

generic - either side, compared by the tables the hop lists.

It does: comparing the schema; comparing row counts; comparing the data itself; the deep checks.

Not yet:

  • carrying sequences and auto-increment values - meanwhile, set each sequence on the target above the source's highest value before cutover
  • comparing server settings - meanwhile, compare the server settings by hand
  • moving a whole database in bulk - meanwhile, move it table by table, or restore a backup of the source
  • copying table by table, resumably - meanwhile, move it with the engine's own backup and restore, and let migkit check prove the result
  • keeping the target following the source - meanwhile, stop writes on the source, move it once, and prove it with migkit check before cutover
  • proving the target has caught up before cutover - meanwhile, stop writes on the source and let migkit check prove the target before cutover
  • telling a difference still arriving from one that is wrong - meanwhile, stop writes on the source before the final check, so nothing is still arriving when it looks
  • verifying only what changed - meanwhile, run migkit check, which compares everything rather than only what changed
  • carrying users and their grants - meanwhile, create the users and their grants on the target by hand
  • noticing a move that moved nothing - meanwhile, run migkit check after the move
  • refreshing the target's statistics after a load - meanwhile, refresh the target's statistics by hand after the load
  • snapshotting the target so a cutover can be rolled back - meanwhile, take a backup of the target yourself before cutover
