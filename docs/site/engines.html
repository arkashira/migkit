Engines

64 engines, any two of them as a pair, and what each can do.

Every engine this version has, and what it can do - read off the code, so this page claims no more and no less than it does. A hop names its two sides by their addresses; migkit's own decision engine finds the fastest, exact, consistent way for each source -> target pair, and says which it chose and why.

What each can do

yes: the code does it for this engine. n/a: it does not apply, and the reason is said. not yet: not done yet, and what to do meanwhile is said. Hover a cell for its reason.

  • schema: comparing the schema
  • counts: comparing row counts
  • data: comparing the data itself
  • deep: the deep checks
  • sequences: carrying sequences and auto-increment values
  • params: comparing server settings
  • bulk-move: moving a whole database in bulk
  • table-copy: copying table by table, resumably
  • stream: keeping the target following the source
  • fence: proving the target has caught up before cutover
  • confirm: telling a difference still arriving from one that is wrong
  • delta: verifying only what changed
  • users: carrying users and their grants
  • guard: noticing a move that moved nothing
  • statistics: refreshing the target's statistics after a load
  • snapshot: snapshotting the target so a cutover can be rolled back

Each shape of table

A table without a key, a key of many columns, a table too large for one range: each shape has a way of its own on each engine, chosen by the decision engine.

  • keyless: a table without a key
  • no unique index: a table with no unique index
  • wide key: a key of many columns or of text
  • too large: a table too large for one range
  • large values: a table with large values
  • partitioned: a partitioned table
  • read-only source: a source that is read-only or a standby
  • missing grant: a user without the grant a program needs
  • read-only target: a target that must stay read-only
  • slow link: a link too slow for one stream
  • writes held: a side whose writes are held and let go again, read back - the source at cutover
  • spread target: a target that spreads a table across nodes of its own, its rows placed and loaded as it places them

Stored code carried and proved

  • the operator's own file: view, function, procedure, trigger, event
  • the query translator: view, function
  • a model: view, function, procedure, trigger, event

It does: comparing the schema; comparing row counts; comparing the data itself; the deep checks; carrying sequences and auto-increment values; comparing server settings; copying table by table, resumably; keeping the target following the source; proving the target has caught up before cutover; telling a difference still arriving from one that is wrong; verifying only what changed; carrying users and their grants; noticing a move that moved nothing; refreshing the target's statistics after a load; snapshotting the target so a cutover can be rolled back.

Does not apply:

  • moving a whole database in bulk: SingleStore loads a whole table through its own loader from a landing store, ranked against the table copier table by table (decide.landing_load): no dump and load of a whole database reaches it
