init

migkit init [OPTIONS]

Set up a hop: in a terminal, asks for the two addresses and the passwords, connects, says what it found and what it will do, and writes the hop. Without one, reads MIGKIT_SOURCE and MIGKIT_TARGET (MIGKIT_SOURCE_PASSWORD, MIGKIT_TARGET_PASSWORD, MIGKIT_GOAL, MIGKIT_HOP), or writes a template to edit.

Installed from a package there is no checkout to copy an example out of, so migkit writes the template itself. Mode 600, because what goes in it next can be a secret's reference.

OptionWhat it does
--herewrite ./conf/hops.yaml in this directory instead of the user config directory
--forceoverwrite an existing file

doctor

migkit doctor [OPTIONS]

What this machine can do, and whether the configured hops connect.

Safe to run before anything is configured - that is the point of it.

Every check/repair/move step migkit runs is a wrapper over a proven external program; --install pulls whichever are missing so any machine or teammate is one command from a full toolchain.

OptionWhat it does
--installauto-install every missing external tool via the platform package manager (brew/apt) - get a fresh machine ready

advise

migkit advise [OPTIONS] HOP_NAME

Show the migration playbook for this hop's service.

assess

migkit assess [OPTIONS] HOP_NAME

Premigration readiness check: CDC prerequisites, risky tables, encoding, extensions, accounts. Run before starting any mover.

schema

migkit schema [OPTIONS] HOP_NAME

Target schema workflows: preparation plan (default), cross-engine DDL conversion (--convert), versioned migration files (--migration).

OptionWhat it does
--dbsingle database
--converttranspile source DDL to the target dialect (hetero hops)
--migrationgenerate versioned V/U migration files from the live schema diff
--applywith --convert: execute the DDL on target
--outwith --migration: output directory

check

migkit check [OPTIONS] HOP_NAME

Read-only validation of target vs source. Never writes to either side.

When counts and data both run, row counts ride along with the checksum query, so nothing is scanned twice. Suspect rows are proven in-flight or real via the replication fence (LSN-based) instead of guesswork.

Ends 0 where the two are the same, 1 where they differ, 3 where the run could not say (an answer not taken, nothing compared, a narrowed run) - verdict.json says which and why.

OptionWhat it does
--dbsingle database
--tablesingle table (schema.table)
--onlycomma list: schema,counts,autoinc,data,deep,params
--deepadd deep checks: fk orphans, disabled triggers, column drift, matview/grants parity, boundary freshness
--drillcolumn-level sample diff for one table (needs --db and --table)
--limitwith --drill: sample rows
--consistentchecksum every table of a db inside one repeatable-read transaction per side, with the src LSN captured as the convergence fence (postgres)
--workersparallel databases, default from conf
--resumeskip checks already ok in last summary
--excludecomma list of db or db.schema.table patterns to skip, added to the hop's

sync

migkit sync [OPTIONS] HOP_NAME

Make target equal to source, or run a whole migration flow.

Default (reconcile) shows/repairs the last check's diffs; --apply executes, --go checkpoints for rollback. --mode runs the whole flow end to end with verification wrapped around every step, so migkit can stand in for a managed migration service on a trusted VM - the same move, the same repair and the same check as the commands of their own, and the exit code the last check's.

OptionWhat it does
--dbone database, or all diffed dbs if omitted
--kind-
--moderun a whole flow: verify (read-only assurance), seed (initial load, then the check and a repair of what differs), stream (follow live changes + delta verify), migrate (load and follow, then the check). default reconcile = repair the last check's diffs
--applyexecute the repair plan, default is dry-run
--gocheckpointed check+repair sweep with rollback state
--servestream and migrate: run the verify loop forever (VM/service)
--interval--serve: seconds between cycles
--on-conflictrows that differ: source-wins overwrites the target (the default, source is truth); keep-target preserves them and fixes only missing/extra. The hop's own on_conflict where not given
--tagwith --go: label this state, e.g. pre-cutover

move

migkit move [OPTIONS] HOP_NAME

Move data for this hop. migkit picks how.

full: the fastest bulk path available for the engine, falling back to a chunked copy that resumes after a crash. A single table always takes the resumable path - restartability matters more than raw speed there. cdc: the engine's native change feed where it has one, otherwise migkit stands up its own streaming pipeline.

There is nothing to choose: the same command does the right thing on every engine, and migkit doctor says what this machine can do. Whatever moves the data, migkit verifies it.

Use only over a trusted network (or run migkit on a cloud VM).

OptionWhat it does
--db-
--tableschema.table (full mode)
--modefull = bulk copy, cdc = follow live changes, full+cdc = initial load plus stream until cutover
--chunkrows per resumable chunk, when a resumable copy is used
--dropcdc modes: tear down replication
--goactually run, default shows the plan

watch

migkit watch [OPTIONS] HOP_NAME

Watch a running migration load: row counts, rate, ETA, replication state. --verify turns it into a continuous validation loop: transient diffs that heal next cycle are replication lag, persistent ones are real. --verify --delta verifies only what changed, so it can run forever against billion-row databases, and says when a flip is safe. With --count it ends as its last cycle's verdict does.

OptionWhat it does
--db-
--intervalseconds between samples (default 30, or 300 with --verify)
--countsamples/cycles then exit, 0 = forever
--verifyre-run read-only checks each cycle instead of sampling row counts (continuous validation)
--onlywith --verify: checks per cycle, add data for full checksum each cycle
--deltawith --verify: O(changes) mode - each cycle re-verifies only the rows touched since the last verified point (WAL slot / binlog / change stream driven)
--teardowndrop the delta slot/position --delta keeps, and exit

report

migkit report [OPTIONS] [HOP_NAME]

Render the HTML report from the last check run and export the hop's evidence (what moved, every verdict with both sides' counts and digests and how to take them again, decisions, approvals, repairs, outages - HTML, Markdown, JSON, CSV), or --serve the live localhost dashboard (with a Prometheus /metrics endpoint).

OptionWhat it does
--openopen in browser
--refreshrender the report again from the last check's answers on disk (no re-check); the answers stay as the check took them
--serveserve the live dashboard for every hop instead of writing a file
--metricsprint Prometheus metrics for every hop and exit (the dashboard also exposes them at /metrics)
--portwith --serve: listen port

history

migkit history [OPTIONS] HOP_NAME

Audit trail: saved rollback states and every write migkit made, read from the local changelog and state journals. migkit writes no bookkeeping into the destination, so the audit is local-only.

OptionWhat it does
--db-
--showprint one state in detail

rollback

migkit rollback [OPTIONS] HOP_NAME

Restore target sequences from a saved state, put back the rows the repairs since it wrote, where the target still holds what they wrote; where the hop streamed back or cut over, the old source's counters raised past the new primary's. With --apply, under one hold of the hop, the application's writes given back last - after everything they would write over is put back.

OptionWhat it does
--db-
--statestate timestamp or tag, default latest
--apply-

users

migkit users [OPTIONS] HOP_NAME {test|create|verify|setpw|rollback}

Sync logins source -> target keeping the same password.

test compare users (read-only), write users.json to the report dir setpw mongo only: set the real passwords on users that already exist on the target, from --passwords (mongo credentials cannot be copied: SCRAM is one-way and DocumentDB blocks writes to system.users) create make the missing users on the target (dry-run unless --apply); mysql copies the password hash = same password, grants replayed from the source; postgres reads passwords from --passwords verify re-compare; exit 0 only when no gap remains rollback drop only the users this command created (dry-run unless --apply)

Cloud system accounts (AWS_*, rds*, tencent*) are excluded on both sides. Never touches the source.

OptionWhat it does
--applyexecute on the target (default is dry-run)
--passwordsyaml file role: password for postgres create and for mongo setpw (managed sources lock password hashes; mysql needs no file - the hash is copied so the password stays identical)

Older names

Names earlier versions used, kept so scripts written for them still run:

NameNow
hopsList configured hops - now part of migkit doctor.
setup-targetNow: migkit schema HOP.
repairNow: migkit sync HOP [--apply].
replicateNow: migkit move HOP --mode cdc / full+cdc. The move itself, with every guard it holds: this alias set a stream up on its own - into a hop that masks, a goal: verify hop, and torn down with no approval and outside the cutover.
tailNow: migkit move HOP --mode cdc --db X - the move itself, with every guard it holds.
convert-schemaNow: migkit schema HOP --convert.
gen-migrationNow: migkit schema HOP --migration.
sample-diffNow: migkit check HOP --drill --db X --table Y.
uiNow: migkit report --serve.
stateNow: migkit history HOP.
monitorNow: migkit watch HOP --verify.
