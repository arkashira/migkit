The web view and the API

Several people, each with a role on each hop, signed in by the organisation's identity provider; a REST API over the command line's own functions.

migkit report --serve serves it: every hop's outcomes - what happens to each side, the time and outage predicted with their spread, the guarantees - its progress, the approvals and the changes on the source waiting for an answer, and the evidence, for the people each hop names, each signed in by the organisation's identity provider. The decision record is shown only when asked. The command line is not needed for any of it, and the view does nothing the command line does not: a run started here is the same command, with the same guards.

Signing in

  • OpenID Connect: the code flow with PKCE; the ID token checked against the provider's published keys, issuer, audience, expiry and nonce (MIGKIT_WEB_OIDC_ISSUER).
  • SAML 2.0: the provider's signed answer to a request this view made, read only out of the element the signature covers (MIGKIT_WEB_SAML_METADATA).
  • SCIM 2.0 at /scim/v2: the provider provisions who may sign in and their groups; a person deactivated there is signed out everywhere at once (MIGKIT_WEB_SCIM_TOKEN).
  • Without a provider, one local operator, the admin of every hop, set once through an address the view prints when it starts.
  • Multi-factor sign-in is the provider's.

Roles

Written in the hops file's access - for every hop, a group of hops by name pattern, or one hop's options.access - by a person's name (shell patterns allowed) or group:NAME. Each role holds the ones before it; nobody has a role the file does not give.

RoleWhat it may do
viewerreads the hop: what it does to each side, the prediction with its spread, the progress, the evidence, the approvals and offers standing, and the decision record when asked
operatoralso starts runs, holds or lets go a change tail, and answers a change on the source a faster way needs
approveralso approves a step the hop's approvals hold back - never one they asked for
adminalso sends the hop's receivers a test message; a global admin also reads the users, groups, sessions and the view's record

The API

Every route is served under /api/v1, answers JSON, and needs an API token made on the account page (Authorization: Bearer ...) or a signed-in page. A hop the caller may not see answers 404; a role too low, 403. The whole description: openapi.json.

Setting it up

On this machine alone, nothing needs setting. Anywhere else it takes TLS - its own certificate, or a reverse proxy in front that does TLS, named so only it is answered. Deployment, the proxy's configuration and each provider's settings: docs/web.md.
